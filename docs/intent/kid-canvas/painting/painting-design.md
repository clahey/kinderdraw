# Painting

## Context and Design Philosophy

Painting is a `@Composable` that owns its own pointer input: it converts whatever pointer stream Compose delivers to it into stroke data, renders it to the drawing surface as it happens, and holds the accumulated drawing until User Experience asks it to save or clear. Per the User Experience LLD's Input Arbitration, Painting only ever receives a pointer that didn't land on any Widgets control — Widgets is composed on top of Painting, and Painting covers the full screen beneath it, so a touch inside no control's hit region simply falls through to Painting's own pointer input, the same ordinary Compose dispatch Widgets' own hit-testing relies on. Painting doesn't arbitrate input itself and doesn't know about Widgets; it takes the screen's `InteractionLock` for the span of its own gesture and observes nothing about the rest of the screen beyond whether that lock refused it (see Composable Shape and Holding the Interaction).

Multiple pointers can hold their own live strokes at once: each pointer that starts drawing gets its own independently tracked stroke, keyed by that pointer's identity, so several fingers touching the canvas concurrently each leave their own mark rather than only the first being recognized. Arbitration only ever decides whether Painting may begin a gesture at all; once Painting holds the interaction, nothing limits how many pointers it may draw concurrently within that gesture (see the User Experience LLD's Input Arbitration).

This is the component the HLD's Compose Multiplatform sharing decision is about: the touch-to-stroke logic and its on-screen rendering are the same implementation across Android and Linux (and iOS later), not just specs kept in sync by convention.

## Composable Shape

Painting's data — the completed strokes and every currently-live stroke in `PaintingState`, and each stroke's own captured points within its `Stroke` implementation — is held as Compose-observable snapshot state (`mutableStateListOf`/`mutableStateMapOf`/`mutableStateOf`) rather than plain Kotlin collections and vars. A thin `@Composable fun Painting(state: PaintingState, lock: InteractionLock, modifier: Modifier)` owns the `Canvas` and the `Modifier.pointerInput` gesture loop that turns raw pointer events into calls against that state. One gesture, in the `awaitEachGesture` sense, spans however many pointers are concurrently down: it begins when a pointer touches down while none was already down, and ends only once every pointer that touched down during it has lifted — the same span `detectTransformGestures`' own multi-finger tracking uses. Within that span, each pointer is tracked independently by its own pointer identity.

Whether the gesture is beginning or ending is decided once per input event — from the net set of pointers still down after every change in that event has been applied — not separately per individual pointer change within the event. A single batched event can report one pointer lifting and a different pointer touching down together; deciding change-by-change would read a momentary empty set in between and spuriously end and restart the gesture, even though nothing was ever actually undown. Splitting the two is what keeps `PaintingState`'s own logic — stroke capture, rendering, `isEmpty()`, `save()`, `clear()` — a plain, directly unit-testable Kotlin class, while the composable itself is the only part that needs an actual Compose UI to exercise.

Because every layer of state that changes as a stroke progresses is Compose-observable snapshot state — not just `PaintingState`'s own stroke list, but each stroke's own captured points (see the Painting Style LLD's Brushes section) — Compose's draw-phase snapshot observation is what triggers a redraw as a stroke grows, with no caller-driven invalidation needed.

`isEmpty()`, `save()`, and `clear()` remain `PaintingState`'s own operations, called directly by whoever holds the state — today, `KidCanvasScreen`; eventually User Experience — via `remember { PaintingState(styleSettings) }`, passing that same instance to both the `Painting` composable and its own lifecycle calls. They aren't routed through the composable, which only ever forwards pointer events into the state it's given.

## Holding the Interaction

Painting asks the `InteractionLock` it was given for the interaction when a gesture begins — an input event carrying a pointer newly down while Painting holds nothing (see Composable Shape for what a gesture spans, and the User Experience LLD's Input Arbitration for why the test is a touch-down rather than any event) — and releases it when that gesture ends, its last remaining pointer lifting. A second, third, or later pointer joining or leaving an already-live gesture asks nothing and releases nothing: the whole multi-pointer span is one hold.

When the lock refuses, Painting's loop never runs, so no stroke is started and nothing reaches `PaintingState` to be undone; the gesture is swallowed to its last pointer's lift.

The release covers every way a held gesture can end, not just the last pointer lifting: if the pointer-input loop is cancelled — the composable leaving composition, or Compose cancelling the gesture — the hold goes with it, so a hold can never outlive the strokes it covered. Strokes still live at that moment stay live in `PaintingState`, which is what Lifecycle Survival relies on; only the hold ends.

Painting learns nothing else about the screen from the lock. It doesn't know what else might be holding it, or why, or whether anything else exists to hold it at all.

## Stroke Model

A stroke is the record of one live pointer's down-to-up sequence: an ordered list of points, plus the brush active when the stroke began (read from `StyleSettings` below). That brush — including whatever color it renders with — is fixed for the stroke's whole duration. Changing the active color mid-stroke can't happen today anyway, since color selection is a Widgets control and Widgets can't receive input while any stroke is live (see the User Experience LLD's Input Arbitration) — but even if it could, an in-progress stroke wouldn't change brush or color retroactively.

Any number of strokes can be live at once, each tracked completely independently and keyed by its own originating pointer: a new pointer touching down starts its own stroke without disturbing any other pointer's already-live stroke, and one pointer's movement, brush, or lift never affects another's. This is what lets several fingers — one toddler's two hands, or several toddlers sharing the same screen — each draw at the same time.

A stroke with only a single point — a tap with no movement — is still a stroke, not discarded: its brush renders it as a small mark, so any touch on the canvas leaves a visible trace.

Each captured point is a `Point` — stored relative to the drawing surface's center and scaled by its shorter dimension at capture time, not a raw pixel coordinate (see the Painting Style LLD's Point section) — so a drawing captured before a resize (the drawing surface's dimensions changing — most commonly a device rotation, within the same lifecycle-survival scope described under Lifecycle Survival) keeps rendering correctly afterward, without Painting needing to detect the resize and rewrite already-captured points itself.

The drawing is the ordered set of all strokes recorded since the canvas was last cleared.

## Style Settings

Painting doesn't own or compute its active brush or its drawing surface's background — it reads both from `StyleSettings`, an interface Painting Style defines (see its Style Settings section). Painting receives its `StyleSettings` reference once, at its own construction, and holds onto it for its whole lifetime — the same reference is used for every later query, whenever a stroke begins or the drawing is cleared.

Painting depends only on the `StyleSettings` interface, not on how an active brush or background — including color — is produced; that's entirely `StyleSettings`' implementation's concern, owned outside both Painting and Painting Style (today, by User Experience — see its LLD's Interaction Feedback).

Painting calls `getActiveBrush()` once per stroke, at the down event that begins it, and immediately asks the returned brush to start a stroke — the brush itself is responsible for resolving and fixing whatever color that stroke renders with (see the Painting Style LLD's Brushes section); Painting doesn't hold onto a brush reference itself. The background is handled differently, since it isn't stroke-scoped: Painting calls `getActiveBackground()` once when constructed and again each time the clear operation is called, and on each of those occasions queries the returned `ColorSource` once for a `Color` it then holds fixed until the next such occasion, reused in between rather than re-read on every render (see Rendering) — except when `PaintingState` is being reconstructed by its lifecycle-survival `Saver`, which supplies the already-resolved color directly instead of triggering a fresh query (see Lifecycle Survival), so an OS-driven recreation can never repaint the background of a drawing already in progress.

## Brushes

Painting itself holds no point-capture or rendering logic of its own: a brush (see the Painting Style LLD's Brushes section) owns a stroke's entire lifecycle, and Painting only forwards pointer events to whichever stroke the active brush created, and asks that stroke to render itself. Painting's one requirement of whatever `Brush`/`Stroke` implementation it's given is that it render incrementally — extending the visible output as each new point arrives — since Painting always renders progressively (see Rendering); Painting Style's `Stroke` interface exists specifically to satisfy that.

## Rendering

Painting renders progressively as a stroke is drawn — each new point extends the visible stroke as it arrives, via the stroke's brush, rather than waiting for pointer-up to render anything. Mechanically, this falls out of Composable Shape's Compose-observable state: a stroke's captured points are read inside the `Canvas`'s own draw phase, so a new point triggers a redraw on its own.

Every render fills the drawing surface with `StyleSettings`' resolved background color first, before any stroke is drawn on top — the same background value on-screen and, since `save()` rasterizes through this same render step (see Save and Clear), in the saved image too. The exact color isn't fixed here; a real product default (see Open Questions) is `StyleSettings`' implementation's concern.

## Save and Clear

Painting exposes three operations to User Experience, which alone decides when to call them (see the User Experience LLD's Lifecycle Behavior):

- `isEmpty()` — true only if no strokes have been recorded since the last clear.
- `save(id: String? = null)` — renders the current drawing to a raster image and writes it to Image Storage (see the Image Storage LLD), returning the resulting entry's id. Called without an id, it creates a new entry. Called with an id — one a caller obtained from an earlier `save()` call on the same drawing — it updates that existing entry in place instead of creating a second one, so a caller that saves the same in-progress drawing more than once (e.g. a future incremental-save feature) doesn't accumulate duplicate entries. Painting itself never remembers an id between calls; passing one back in on a later call is entirely the caller's responsibility, since only the caller knows whether the current drawing continues one it already saved. Painting owns the write itself; it's the component with the direct relationship to Image Storage.

`save()` isn't called from within an active composition frame, so it rasterizes off-screen: it draws the same strokes and brushes that `render()` would draw on-screen into a fresh `ImageBitmap` — the type Image Storage's create and update operations accept (see the Image Storage LLD's Data Shape) — sized to the drawing surface's dimensions as of the most recent `render()` call. Painting remembers that size across renders for this purpose; `save()` never needs the caller to supply it. If `save()` is ever reached before any `render()` call has happened, the drawing surface's size is unknown; rasterization falls back to a minimal 1×1 image rather than failing, since no `render()` call means nothing has been drawn to preserve anyway.
- `clear()` — discards all recorded strokes and resets the visible drawing surface to blank, re-querying `StyleSettings`' resolved background for the drawing that starts next (see Style Settings).

User Experience calls `isEmpty()` first, calls `save()` only if it returns false, then always calls `clear()`. Today's New Picture sequence always calls `save()` without an id, since each drawing is saved exactly once, right before it's cleared — the id parameter exists for a future caller that saves the same in-progress drawing more than once. Painting itself never decides whether to save — only whether there's anything to save.

If the write to Image Storage fails, `save()` reports that failure to its own caller rather than treating the drawing as saved — a caller that isn't told a save failed can't retry or warn a parent, and User Experience's own auto-save-then-clear sequence must not clear a drawing it never actually persisted.

`clear()` is only ever called when no stroke is active, per User Experience's Input Arbitration — but it's well-defined even if that guarantee didn't hold: every stroke still in progress at that moment (its pointer hasn't lifted) is finalized as it currently stands, discarded along with everything else, and immediately replaced by a new stroke continuing from that same pointer's current location — independently, per pointer, so one interrupted stroke's replacement never gets confused with another's. This is deliberately *not* the same as a real lift-and-touch-again: each replacement stroke carries forward its own interrupted stroke's already-resolved color rather than the brush resolving a fresh one from its `ColorSource`, since that pointer never actually lifted and nothing about the toddler's held touch changed (see the Painting Style LLD's Brushes section). This keeps every still-active touch tracked, with its own settings undisturbed, rather than silently dropped or arbitrarily re-colored. One consequence worth naming: `isEmpty()` called right after such a mid-stroke `clear()` returns false whenever at least one pointer was still down, since each replacement stroke already has one point — the same zero-movement-tap rule from Stroke Model.

## Lifecycle Survival

The current drawing must also survive the OS-managed lifecycle events described in the User Experience LLD (rotation, brief backgrounding, saved-instance-state-scoped process death). All of these are treated identically, restoring every stroke that had already completed before the event, plus — for every stroke still in progress at that moment, however many pointers that was — each one finalized using whatever points it had captured so far, the same points-so-far finalization the mid-stroke `clear()` behavior already performs per pointer (see Save and Clear) — but without that behavior's second half: no replacement stroke begins for any of them afterward, since no live pointer survives an OS-driven recreation to continue from. No stroke a toddler actually touched is ever silently dropped, whether or not its pointer had lifted yet, regardless of how many fingers were down at once.

Configuration changes and actual process death aren't distinguished here, even though they sound like they should be: the platform's own saved-instance-state mechanism (`onSaveInstanceState`/Compose's `rememberSaveable`) runs identically for both — it can't tell in advance whether a given backgrounding will end in process death, so it always persists proactively — and a live touch gesture gets cancelled by the OS on *any* UI recreation regardless of whether the process itself survives. So there's no scenario where a genuinely still-live, still-trackable gesture carries through to the other side; the only question is ever "what had this stroke captured by the time persistence ran," which is answered the same way either way.

Restoring the drawing never invokes `save()` — routine lifecycle churn shouldn't produce a permanently saved drawing; only calling `save()` does that.

`PaintingState` is held via `rememberSaveable`, using a `Saver` built as a factory function closing over the current `StyleSettings` (needed only to reconstruct `PaintingState` — `StyleSettings` isn't itself part of what's saved). `PaintingState` owns its own serialization the same way a `Stroke` owns its (see the Painting Style LLD's Save and Restore): `toSavedState()` returns a self-describing `Map<String, Any?>` — its currently-cached background `Color`, plus every stroke's own `save()` result, every completed stroke and the live one too if one is in progress at that moment, its `save()` call capturing whatever points it has so far. The `Saver`'s `save` is just `state.toSavedState()`.

`PaintingState`'s constructor accepts that same map back as an optional `savedState` parameter, unset by default. Ordinary construction (`remember { PaintingState(styleSettings) }`) leaves it unset, so `PaintingState` resolves its own background from `StyleSettings` and starts with no strokes, exactly as it always has. When `savedState` is supplied, the constructor reads the saved background `Color` directly (no fresh `StyleSettings` query) and calls `styleSettings.getActiveBrush().restore(entry)` per saved stroke entry to reconstruct the stroke list (exact by construction with today's single brush type) — all as completed strokes, none live, matching the "finalized, not continued" behavior above. The `Saver`'s `restore` is just `PaintingState(styleSettings, savedState = saved)`. Painting's own persistence code never inspects what's inside a saved stroke's map.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Zero-movement tap | Recorded as a single-point stroke, rendered as a mark by its brush | Discard taps with no movement as not a real stroke | A toddler tapping the canvas expects a visible mark for any touch; discarding silent no-ops contradicts the immediate-response philosophy from the User Experience LLD. |
| Stroke rendering | Progressive, point-by-point as the stroke is drawn | Render only on pointer-up, once the full stroke is known | The toddler is actively touching the screen; waiting until lift to show anything would mean no visible response while they're mid-action. |
| Who writes a saved drawing to Image Storage | Painting itself, on a `save()` call from User Experience | User Experience writes to Image Storage directly, using drawing data pulled from Painting | Matches the Kid Canvas sub-HLD's system diagram, where Painting owns the "writes drawings" edge to the store, and keeps Image Storage access confined to the component that already owns the drawing data. |
| Saved-drawing format | A rendered raster image | Vector/stroke data | The HLD's Non-Goals exclude re-editing or undo history, so nothing ever needs to reconstruct strokes from a saved drawing — only display and delete it (see the Image Storage LLD). |
| Source of a stroke's active brush | Painting calls `StyleSettings.getActiveBrush()` and immediately asks the returned brush to start the stroke | Painting holds an active brush as its own mutable state, set via a setter call from User Experience | Keeps whatever decides the brush — today's single default type, or any future automatic behavior — entirely outside Painting, mirroring Config's raw/resolved separation. Painting only ever needs to ask the current brush to start a stroke, not know how it was chosen. |
| `save()` failure handling | Reports the failure to its own caller rather than treating the drawing as saved | Silently behave as if the write succeeded | Matches Image Storage's own contract of reporting failures rather than crashing; a caller not told a save failed can't retry or warn a parent, and it must not clear a drawing that was never actually persisted. |
| Raster image production for `save()` | Off-screen rendering via a `CanvasDrawScope`, replaying the same brush `render()` calls used for on-screen display into an `ImageBitmap` | Capture already-rendered on-screen pixels directly | Reuses the exact rendering path already used on-screen, so the saved image is guaranteed pixel-identical to what's currently visible, and doesn't depend on `save()` being called from within an active composition frame the way capturing on-screen pixels would. |
| Rasterization pixel size for `save()` | Painting remembers the drawing surface's size from its most recent `render()` call and rasterizes at that size, falling back to 1×1 if no `render()` call has happened yet | User Experience passes the current canvas size into `save()` explicitly; let rasterization fail/crash if no size is known yet | `save()` isn't called from within an active composition frame, so a size has to come from somewhere; remembering the last-rendered size keeps User Experience from needing to know or track canvas dimensions itself, consistent with rendering detail staying inside Painting. A render-less `save()` is expected to be rare (progressive rendering means a size is normally known by the time there's a stroke to save) but isn't otherwise prevented, so a 1×1 fallback keeps it a well-defined no-op rather than a crash. |
| `clear()` called while a stroke is live | Finalize the in-progress stroke as-is, discard it with everything else, then immediately start a new stroke continuing from the same pointer location and carrying forward the same already-resolved color | Silently drop the live stroke and stop tracking that pointer; reject/ignore the call while a stroke is live; treat it exactly like a real lift-and-touch-again, letting the brush resolve a fresh color for the replacement stroke | Today's Input Arbitration guarantees this never happens, but a well-defined behavior costs little to specify and avoids leaving a still-active touch untracked if that guarantee ever changes. Resolving a fresh color would risk an arbitrarily different one mid-gesture even though the toddler's hand never left the screen — the pointer didn't actually lift, so nothing about the held touch should change. |
| Lifecycle survival scope | One spec covering configuration change, brief backgrounding, and process death uniformly: every completed stroke restored, plus a live-at-persistence-time stroke finalized using its points-so-far | Split into two specs — full state (including a still-live, still-trackable stroke) surviving configuration change via plain object retention; only completed strokes surviving process death | Originally split on the theory that a config change could preserve a live, continuously-trackable gesture via in-memory retention, unlike process death. That theory doesn't survive contact with how Android's saved-instance-state mechanism actually works: it runs identically for both triggers (it can't know in advance which one it's facing), and a live touch gesture is cancelled by the OS on any UI recreation regardless — so there was never a scenario where the two specs would actually describe different platform behavior. |
| How `PaintingState` survives OS-driven recreation | `rememberSaveable` with a custom `Saver`, built as a factory function closing over `StyleSettings` | `rememberSaveable` with a custom `Saver` capturing no external context; hoisting `PaintingState` outside the recomposed scope entirely (e.g. a retained holder above the Activity's own Composition, such as a `ViewModel`) | A `Saver`'s `restore` is a pure function of only the saved data, so reconstructing `PaintingState` (which needs a live `StyleSettings` reference) requires capturing one via closure when the `Saver` is built. A retained-holder approach was considered and rejected: it would need a second, separate mechanism for actual process death anyway (retained holders don't survive that), while a `Saver`-based mechanism handles both triggers uniformly in one mechanism, and the data being persisted (a toddler's drawing — at most a few hundred points and colors) is cheap enough to serialize that skipping it for configuration changes specifically would save an imperceptible amount of work at the cost of building and maintaining two mechanisms instead of one. |
| Where a stroke's saved data is interpreted | `PaintingState` itself, both when building its own `toSavedState()` map and when reading a `savedState` constructor argument back — each stroke's own entry stays an opaque `Map<String, Any?>` produced by `Stroke.save()` and consumed by `Brush.restore()` (see the Painting Style LLD's Save and Restore) | Painting's own persistence code reads a stroke's points and color directly; keep `PaintingState`'s own state opaque to itself too, with an external `Saver` function assembling/disassembling the map from separate accessors | Keeps Painting from needing to know how any given brush represents a stroke internally, the same encapsulation `startStroke()` already provides for live strokes. Having `PaintingState` build and read its own saved-state map (mirroring `Stroke.save()`/`Brush.restore()`) keeps the map's shape — its key names — private to the one type that owns it, rather than shared knowledge between `PaintingState` and an external `Saver` function reaching into it via accessor methods. |
| How a restored background color and stroke list reach `PaintingState` | `PaintingState`'s constructor takes the same `Map<String, Any?>` `toSavedState()` returns, as a single optional `savedState` parameter, unset by default; unset means resolve/start-empty as before, and only the `Saver`'s restore path supplies it | (1) Two separate optional parameters (a resolved `Color`, an initial stroke list), with the `Saver` responsible for taking `toSavedState()`'s map apart into them; (2) a non-optional `Color` parameter, pushing resolution out to every construction call site, including the ordinary one; (3) give `ColorSource` its own restore mechanism (e.g. `RandomColor` remembering and being able to reproduce its last output) | A single `savedState` parameter mirrors `toSavedState()`'s own shape exactly, so the constructor is the one place that reads the map apart, matching the "who interprets a stroke's saved data" decision above rather than splitting that job between `PaintingState` and the `Saver`. Keeps the one existing, ordinary construction call site (`remember { PaintingState(styleSettings) }`) completely unchanged. Teaching `ColorSource` to reproduce a past output would add state and complexity no other caller needs, just to route around a problem `PaintingState`'s own constructor can solve directly. |
| How Painting obtains its `StyleSettings` reference | Constructor-injected and held for the instance's whole lifetime | Passed as a parameter to each method that needs it (`onPointerDown`, `render`, `save`) | Painting already needs a lasting reference for per-stroke brush queries; injecting once at construction gives the background accessor (queried on its own schedule, not per call) a natural place to be read from, instead of threading the same dependency through every call site. |
| Source of the drawing surface's background | A `Color` Painting resolves itself from `StyleSettings.getActiveBackground()`, filled before drawing strokes | A visual-design decision left to whatever's behind Painting in the UI tree; a caller-supplied background parameter on `render()`/`save()` | Deferring to "whatever's behind it" works on-screen but has nothing to fall back to in a saved, standalone image — a saved drawing would come out with a transparent background instead of looking like a normal picture. Painting filling a real, resolved background itself gives on-screen and saved output the same background by construction, since both go through the same `render()` step. |
| Background query timing | `getActiveBackground()` called once when Painting is constructed, and again on each `clear()` call; the `Color` resolved from it at each of those moments is reused in between, not re-read per render | Re-read on every render (like nothing is cached); resolved once ever, for the instance's whole lifetime, never revisited | This is a user-behavior guarantee, not a caching optimization: a re-render triggered by something other than the toddler starting a new drawing — most notably an OS-driven recreation such as rotation — must never change the background of a drawing already in progress out from under them, and a randomized background must pick its new value only for the next drawing, not retroactively alter the current one. Tying the query to construction and `clear()` means a background change only ever happens at an explicit new-drawing boundary; re-reading per render would let an unrelated re-render silently change the current drawing, and resolving only once ever would prevent a randomized background from ever varying between drawings at all. |
| `save()`'s id parameter and return value | Optional `id` parameter, defaulting to none (create); returns the resulting entry's id | A separate method (e.g. `update()`) mirroring Image Storage's own create/update split; `save()` always creates, with any future incremental-save feature managing its own separate write path outside Painting | One save path handles both a drawing's first save and a later save of the same in-progress drawing, mirroring Image Storage's own id-is-an-opaque-handle model: a caller just passes back whatever `save()` last returned. Returning the id (rather than `Unit`) is what makes that possible — without it, a caller could never obtain an id to pass into a later call at all. |
| Hoisted Compose state vs. a plain class with a caller-driven redraw trigger | `PaintingState` holds strokes as Compose-observable snapshot state (`mutableStateListOf`/`mutableStateOf`); a thin `@Composable fun Painting(state, lock, modifier)` wrapper owns the `Canvas` and pointer input | A plain class exposing its state as ordinary Kotlin collections/vars, with whoever hosts the `Canvas` bumping a manual counter on every pointer event to force a redraw; a `Flow`-based reactive read the composable collects | Compose's own snapshot system already solves exactly this — a redraw triggered by the toolkit's own draw-phase observation, not by a caller-maintained invalidation signal. |
| Where a stroke's own captured points live | Compose-observable (`mutableStateListOf<Point>`) inside each `Stroke` implementation (see the Painting Style LLD's Decisions & Alternatives), not just at the `PaintingState` level | — (see the Painting Style LLD's "`AbstractSimpleBrush`'s stroke's internal point storage" row) | Progressive per-point redraw needs the point-list read inside a stroke's own `render()` to itself be a snapshot-state read; wrapping only the outer stroke reference at the `PaintingState` level would still miss point-by-point changes within one still-live stroke. |
| Tracking multiple concurrent live strokes | Keyed by each pointer's own identity, in a Compose-observable map from pointer to that pointer's own live `Stroke` | Keep a single live-stroke slot and drop every pointer after the first; track concurrent strokes by insertion order or z-index without pointer identity | A pointer identity is the natural, already-available key Compose provides per touch, and is exactly what's needed to route each pointer's own down/move/up sequence to its own stroke without cross-talk between fingers — an order- or index-based key would need Painting to invent an identity Compose already hands it for free. |
| What a gesture spans with multiple concurrent pointers | One gesture — and one hold on the interaction lock — spans from the first pointer touching down while none was down, to the last one lifting, however many pointers came and went in between: the same multi-pointer gesture span `awaitEachGesture`/`detectTransformGestures` already use elsewhere in Compose | Acquire and release per individual stroke, so each pointer takes its own hold; keep a single-pointer-only gesture span and simply stop tracking pointers beyond the first | Arbitration only ever needs to know whether Painting is busy at all, so a per-pointer hold would have to be a counted or shared lock — a strictly more complicated mechanism to express the same exclusion, and one where a second finger's hold could outlive the first's. Reusing Compose's own multi-pointer gesture span makes the hold's span exactly the span the toolkit already tracks. |
| Upper limit on concurrent live strokes | None imposed by Painting — every pointer Compose delivers gets its own stroke | A fixed product-level cap, dropping pointers beyond it | The touchscreen hardware and OS already limit how many simultaneous touch points can ever be reported at all; an additional cap in Painting would just be an arbitrary second limit with no toddler-usability motivation behind picking any particular number. |
| Who owns pointer input | The `Painting` composable itself, via its own `Modifier.pointerInput` | User Experience drives `onPointerDown`/`onPointerMove`/`onPointerUp` calls into Painting directly (Painting's earlier shape) | Matches the same ordinary-Compose-dispatch model Widgets already uses for its own hit-testing (see the User Experience LLD's Input Arbitration) — Painting is no longer the one component whose input is routed through a caller instead of through Compose itself. |
| How Painting participates in arbitration, given it owns its own pointer input | Takes an `InteractionLock` parameter and holds it for its gesture's span, refusing to start a stroke when the lock refuses it | Report liveness outward instead (an `onStrokeActiveChange: (Boolean) -> Unit` callback parameter, or a `Flow<Boolean>`) and let User Experience block on Painting's behalf | Painting knows its gesture's real span — including cancellation — better than any observer reconstructing it from callback edges, and a `finally` around the held span releases on every exit path a reported boolean could get stranded on. A composable also has no persistent object identity to hang a `Flow` off of. |

## Open Questions & Future Decisions

### Resolved

1. ✅ Painting is a hoisted-state Compose pattern — `PaintingState` holds Compose-observable snapshot state, and a thin `@Composable fun Painting(...)` wrapper owns pointer input and takes the interaction lock for its own gesture. See Composable Shape and Holding the Interaction.
2. ✅ A resolved brush's color can change automatically between strokes, without a new toddler tap — Painting's read-once-per-stroke behavior already accommodated this either way, and User Experience's `StyleSettings` implementation now does exactly this via `RandomColor`. See the User Experience LLD's Interaction Feedback.
3. ✅ `Point` moved into Painting Style, and `StyleSettings`' accessors were renamed `getActiveBrush()`/`getActiveBackground()` — see the Painting Style LLD's Point and Style Settings sections.
4. ✅ `PaintingState` survives OS-driven recreation (configuration change, brief backgrounding, and process death, treated uniformly) via `rememberSaveable` with a custom `Saver`. See Lifecycle Survival and Decisions & Alternatives.
5. ✅ Painting tracks multiple concurrent live strokes (true multi-touch drawing), keyed by pointer — several fingers touching the canvas at once each get their own independently tracked stroke, rather than only the first pointer being recognized. See Stroke Model, Holding the Interaction, and Decisions & Alternatives.

### Deferred

1. How the shared Compose Multiplatform canvas embeds inside the native GTK+ shell on Linux is an open technical question at the HLD level, inherited here without further resolution.
2. How Painting's restoration mechanism identifies which brush *type* originally produced a saved stroke — so it can `restore()` on the right one instead of always the currently active brush — is the Painting Style LLD's own open question (see its Open Questions #4 and #6), not decided here. With exactly one brush type today, always using the active brush is exact by construction.
3. Painting re-renders every completed stroke from scratch each frame rather than caching them into an off-screen bitmap once they stop changing. This costs more per frame as a drawing accumulates strokes, but no measured performance problem has shown up yet to justify a cached-bitmap rendering path.
4. Painting's own test suite (stroke capture, rendering, save/clear) only runs against the JVM target's Skia-backed graphics; it doesn't independently verify against Android's own Compose actuals, since a `kotlin.test` class can't carry Robolectric's JUnit4 runner annotation without breaking compilation for the JVM target too. This rests on Compose Multiplatform's cross-backend consistency contract rather than direct evidence for the Android backend specifically. Whether that's worth closing — a source-set split, a different multiplatform test-runner mechanism, or something else — isn't decided here.
5. `StyleSettings`' active background has no product selection surface today — no Widgets control lets anyone choose it, so a real implementation returns a fixed default (see the User Experience LLD's Interaction Feedback for today's actual choice). Whether background ever becomes user-facing, and if a change made mid-drawing should take effect immediately rather than waiting for the next `clear()` (today's construct-and-clear-only query schedule), isn't decided here.
6. `save()`'s optional id parameter (see Decisions & Alternatives) has no caller that uses it yet — today's only caller, User Experience's New Picture sequence, always saves a drawing exactly once and never passes one back in. Which future feature (an incremental autosave while drawing, most likely) becomes that caller, and how it obtains and holds onto the id between saves, isn't decided here.
7. Painting's multi-touch guarantee (any number of concurrent live strokes) is only as real as whatever blocking mechanism eventually keeps other pointers off Widgets during a live gesture — see the User Experience LLD's Input Arbitration, not yet updated for multi-touch. If that mechanism ends up blocking the whole screen, including Painting, rather than Widgets specifically, concurrent strokes would be silently prevented from ever starting once Widgets lands, contradicting this LLD's own guarantee. Not resolved here — deferred until Input Arbitration is revisited alongside Widgets' actual implementation.
8. Stacking order between two concurrently-live strokes that visually overlap is unspecified — whichever renders on top is an artifact of the underlying map's iteration order, not of which pointer started first, moved last, or any other user-meaningful rule. On-device testing confirmed this reads as one stroke consistently winning over another for a given pair of touches, which can look arbitrary when two toddlers' strokes cross. Rare enough in practice, and with no clearly better rule obviously in hand (start order? most-recently-moved on top? something else?), that it isn't worth fixing now — left as a known, deliberately deferred rough edge rather than a bug.
