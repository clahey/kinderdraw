# User Experience — EARS Specs

## Screen Composition

- [x] **CANVAS-UX-001**: When the kid canvas screen is composed, the system shall render Painting full-bleed as the drawing surface and compose Widgets controls as chrome anchored along the screen's edges on top of it, so no control ever sits over the drawing area. Transient presentation the screen itself raises over the drawing area — the save feedback of CANVAS-UX-031 through CANVAS-UX-034 — is layered between the two and is not a control: it accepts no input (see CANVAS-UX-035) and outlives no gesture.

## Input Arbitration

- [x] **CANVAS-UX-002**: When a pointer touches down inside some Widgets control's hit region and no component holds the interaction, the system shall grant the interaction to that control, which claims the pointer.
- [x] **CANVAS-UX-003**: When a pointer touches down outside every Widgets control's hit region, and either no component holds the interaction or Painting itself is the holder, the system shall route that pointer to Painting instead, starting a stroke — even when the touch missed a nearby control's hit region.
- [x] **CANVAS-UX-004**: While one component holds the interaction, the system shall refuse it to every other component, so no other Widgets control can claim a pointer and no stroke can start on Painting.
- [x] **CANVAS-UX-005**: When a component is refused the interaction, the system shall keep that refusal in force for the remainder of that component's gesture — a pointer already down when the holder releases stays inert until it lifts and touches down again, and only a subsequent pointer-down is eligible to start the next gesture.
- [x] **CANVAS-UX-020**: The system shall grant the interaction to at most one component at a time, refusing every request made while it is held.
- [x] **CANVAS-UX-021**: The system shall provide no way to release the interaction other than through the hold object a successful request returned, so a component that never acquired the interaction cannot release it. This is a property of the type's surface rather than of its behavior, so it carries no test: violating it would fail to compile.
- [x] **CANVAS-UX-022**: When a hold that has already been released is released again, the system shall leave the interaction's current holder unchanged, so a stale hold cannot free a later holder's interaction.
- [x] **CANVAS-UX-023**: The system shall request and release the interaction only from the UI dispatcher, and shall carry no synchronization of its own. A control's release after a suspending activation satisfies this by running in a composition-tied scope — see CANVAS-WIDGETS-024. Being an invariant over every call site rather than a triggered behavior, this carries no test of its own; each call site's own tests exercise it.
- [x] **CANVAS-UX-024**: When the kid canvas screen is composed, including after an OS-driven recreation, the system shall start with the interaction unheld rather than restoring any hold in effect beforehand.
- [x] **CANVAS-UX-027**: The system shall request the interaction only on an input event carrying at least one pointer newly touching down, and only while the requesting component isn't already holding it — so a hovering pointer never takes the interaction, and a pointer joining a gesture already held doesn't request a second time. The hover half is verified by inspection rather than by test — the test harness injects touch, and a touch pointer is always pressed, so no test can construct a hovering one.
- [x] **CANVAS-UX-026**: When two pointers touch down in the same input event, one inside a Widgets control's hit region and one outside every control's hit region, the system shall grant the interaction to exactly one of them and refuse the other. Which one wins is unspecified — the two requests race, and either outcome is acceptable. Layering decides only which component a *single* pointer reaches at all, per CANVAS-UX-002 and CANVAS-UX-003. The exactly-one-wins half is verified at the lock itself rather than through the screen: the test harness enqueues each touch-down as its own input event, so two pointers arriving in one event can't be constructed from a test.

## Feature Gating

- [D] **CANVAS-UX-006**: When composing the screen, the system shall include only the Widgets controls and optional behaviors whose backing feature Config resolves as on, omitting the rest entirely rather than rendering them disabled.
- [D] **CANVAS-UX-007**: The system shall gate today's canvas feature set (color picker, New Picture) as a single bundle, resolved as one unit rather than per-feature.
- [D] **CANVAS-UX-008**: When Config's resolved feature values change while a gesture is live, the system shall defer applying the resulting composition change until that gesture ends, rather than recomposing mid-gesture.

## Lifecycle Behavior — New Picture

- [x] **CANVAS-UX-009**: When New Picture's pointer is claimed, the system shall hold the interaction from that moment through that same pointer's release, so no other control-press or stroke can start during the press itself — regardless of whether the release goes on to activate New Picture.
- [x] **CANVAS-UX-019**: When New Picture activates, the system shall run the sequence below as that activation's own work, under the hold its press already took, keeping that hold until the sequence ends — including any save feedback it shows, and whether it ran through to the clear or stopped early at a failed save — rather than releasing it at the press's own release.
- [x] **CANVAS-UX-010**: When the New Picture sequence runs, the system shall first ask Painting whether the current drawing is empty.
- [x] **CANVAS-UX-011**: When the New Picture sequence's emptiness check reports the drawing is not empty, the system shall call Painting's save operation with no id, so Image Storage creates a new entry, before clearing.
- [x] **CANVAS-UX-012**: When the New Picture sequence's emptiness check reports the drawing is empty, the system shall skip the save call entirely, writing nothing to Image Storage.
- [x] **CANVAS-UX-013**: When the New Picture sequence's save succeeds, or its emptiness check skipped the save entirely, the system shall clear Painting's canvas — a sequence with nothing to write still clears — and shall do so before showing any save feedback (see CANVAS-UX-031). A sequence whose save failed never clears (see CANVAS-UX-029).
- [x] **CANVAS-UX-028**: When the New Picture sequence's save call reports a failure, the system shall call Painting's save operation exactly once more, immediately and with no intervening delay.
- [x] **CANVAS-UX-029**: When the New Picture sequence's retried save also reports a failure, the system shall not clear Painting's canvas, leaving the drawing exactly as it stood. The sequence continues only into its save feedback (see CANVAS-UX-032), which alters nothing it draws over.
- [ ] **CANVAS-UX-014**: The system shall show no confirmation dialog for the New Picture sequence, and shall present nothing within it that requires a response from the toddler before drawing can resume — the toddler can resume as soon as the sequence ends, including its save feedback.
- [x] **CANVAS-UX-025**: When an OS-driven recreation cancels a New Picture sequence, the system shall resume no part of it, and shall show on the restored screen whatever that sequence had already committed to Painting — the drawing untouched if the clear hadn't run, the cleared canvas if it had — with no save feedback around it. Verified by inspection rather than by test — see the LLD's Open Questions.

## Lifecycle Behavior — Putting the Drawing Away

- [x] **CANVAS-UX-030**: When the New Picture sequence's emptiness check reports the drawing is not empty and the save feedback's animation is going to run, the system shall obtain a raster snapshot of the drawing from Painting (see CANVAS-PAINT-025) before clearing the canvas, and shall use that image as the subject of CANVAS-UX-040, CANVAS-UX-031 and CANVAS-UX-032. When that animation is suppressed (see CANVAS-UX-037), no snapshot is taken — nothing would display it. That second half is verified by inspection rather than by test: `PaintingState` is a concrete class, so there is no seam through which a test could count snapshot calls.
- [x] **CANVAS-UX-042**: While the save feedback's animation runs, the system shall cover the drawing surface with an opaque white field, from the moment CANVAS-UX-040's lift begins until the feedback ends. The field is the bare surface between two sheets rather than a rendering of the canvas, so it is white irrespective of what background `clear()` resolves.
- [x] **CANVAS-UX-038**: When the system first displays the snapshot for CANVAS-UX-040, it shall cover the drawing surface at the same position and size the drawing occupied, so that first frame is indistinguishable from the canvas it replaces.
- [x] **CANVAS-UX-040**: When the New Picture sequence has taken its snapshot, the system shall immediately animate that snapshot shrinking where it stands until it no longer overlaps the New Picture button and then crossing to rest at that button, overlapping its top edge, without waiting for the save's outcome; if the save has not yet reported when the movement finishes, the snapshot shall remain there until it does.
- [x] **CANVAS-UX-044**: Where the system splits one apparent gesture into consecutive movements — shrinking then crossing to the button, or turning back then growing home — it shall carry speed across the join rather than coming to rest at it, so the pair reads as one movement. Verified by inspection rather than by test: a test can read a position per frame but not whether the resulting motion looks continuous.
- [x] **CANVAS-UX-043**: The system shall draw the travelling snapshot above the New Picture button only while it is crossing to that button, resting at it, or leaving it, and beneath the button at every other point. Each change of layer shall fall where the snapshot does not overlap the button, so no change of layer is ever visible. Where the movements alone do not produce such a moment — before CANVAS-UX-031's descent, which begins from a snapshot resting *on* the button — the system shall first animate the snapshot hopping clear of it. The hop is tested; the layering it enables is verified by inspection, since which of two overlapping nodes paints first has no presence in the semantics tree.
- [x] **CANVAS-UX-031**: When the New Picture sequence's save succeeds, the system shall animate the snapshot descending from CANVAS-UX-043's hop into the New Picture button, drawn beneath that button so the button occludes it as it enters, and then remove it.
- [x] **CANVAS-UX-041**: When CANVAS-UX-031's descent completes, the system shall obtain a second snapshot — of the canvas as cleared per CANVAS-UX-013 — animate it entering from wholly off screen on the opposite side of the drawing surface from the New Picture button, travelling to the same reduced, centred position a departing snapshot passes through, and growing from there until it comes to rest filling that surface, and then remove both it and CANVAS-UX-042's cover, revealing the live canvas beneath without a change in what is displayed.
- [x] **CANVAS-UX-032**: When the New Picture sequence's save fails on both attempts, the system shall animate the snapshot retracing CANVAS-UX-040's path — away from the New Picture button to where it last cleared it, then growing back to the position and size it started at — and then remove it and CANVAS-UX-042's cover together. No second snapshot is taken and no sheet arrives, because nothing was taken away, and Painting's drawing is left unmodified throughout.
- [x] **CANVAS-UX-033**: When the New Picture sequence's save fails on both attempts, the system shall show a transient red flash that expands from the New Picture button until it covers the drawing surface, brightening and then fading over its own duration — timed, whenever CANVAS-UX-032's animation runs, to the moment the snapshot begins turning back from the button. The flash does not depend on that animation running (see CANVAS-UX-037).
- [x] **CANVAS-UX-034**: While either snapshot is animating, the system shall draw a border around it, and shall have removed that border wherever a snapshot comes to rest filling the drawing surface — CANVAS-UX-032's rebound and CANVAS-UX-041's arrival — so that final frame matches the canvas handed back beneath it. Verified by inspection rather than by test — a border is a paint property with no presence in the semantics tree, and exposing one purely to assert on would be test-only API for a visual detail.
- [x] **CANVAS-UX-035**: The system shall accept no pointer input on either animating snapshot, the cover, or the red flash — none of them may claim the interaction, consume a pointer, or be treated as the target of a touch.
- [x] **CANVAS-UX-036**: When the New Picture sequence's emptiness check reports the drawing is empty, the system shall take no snapshot and show no save feedback — no cover, no animation, no flash.
- [x] **CANVAS-UX-037**: While the reduced-motion preference supplied to the kid canvas screen is set, the system shall omit the animations of CANVAS-UX-040, CANVAS-UX-031, CANVAS-UX-041 and CANVAS-UX-032 entirely, along with CANVAS-UX-042's cover, while still showing CANVAS-UX-033's red flash when the save failed. The preference is passed into the screen rather than queried from the platform at the point of use, and is read once when the sequence reaches its feedback, so a change arriving mid-flight never applies partway through one.
- [A] **CANVAS-UX-039**: The system shall supply CANVAS-UX-037's preference from the platform's own reduced-motion setting, re-reading it whenever that setting changes. On Android the setting is `Settings.Global.ANIMATOR_DURATION_SCALE`, which both the "Remove animations" accessibility toggle and the developer-options animator scale write, and only a value of zero — play no animations — is a request for reduced motion; any other value, however stretched or shortened, is a request for animation rather than against it. That the value is re-read live is verified by inspection rather than by test; the reading itself is tested.

## Lifecycle Behavior — OS Navigation and Process Lifecycle

- [D] **CANVAS-UX-015**: When the OS back gesture or button fires while the kid canvas is shown, the system shall consume it and not navigate the toddler out of the kid canvas.
- [D] **CANVAS-UX-016**: When the OS recreates the process's UI within its own saved-instance-state mechanism (a configuration change, brief backgrounding, or process death within that scope), the system shall preserve the current in-progress drawing exactly as it stood, without invoking the New Picture save path. Deferred alongside Painting's CANVAS-PAINT-011 and CANVAS-PAINT-019, which this depends on.

## Interaction Feedback

- [D] **CANVAS-UX-017**: When a color swatch is activated, the system shall write that color into `StyleSettings` as the color for the next resolved brush instance, so Painting's next stroke starts in the new color with no separate acknowledgment step.
- [ ] **CANVAS-UX-018**: The system shall accompany the New Picture sequence with no banner, toast, or text of any kind — a pre-literate toddler cannot read one, and nothing it shows may require dismissal. The sequence's own feedback is the drawing's motion (see Lifecycle Behavior — Putting the Drawing Away).
