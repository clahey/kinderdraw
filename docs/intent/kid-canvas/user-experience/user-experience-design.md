# User Experience

## Context and Design Philosophy

User Experience is Kid Canvas's composition root: it arranges Widgets (buttons, color picker, and similar chrome) and Painting (the drawing surface) into one screen, and owns whatever behavior belongs to the screen as a whole rather than to either child on its own — which controls are present, what happens when a lifecycle action fires, how touches are arbitrated between drawing and chrome, and how the screen answers a toddler's action immediately. Widgets and Painting don't depend on each other; User Experience is the only component that depends on both. The one thing they take back from User Experience is the interaction lock defined here (see Input Arbitration) — the arbiter each of them holds in turn, and the only channel through which either learns that some *other* gesture is live, without learning whose.

The toddler-usability tenet governs every decision here: no confirmation dialogs, no state a toddler has to interpret before continuing, no visible-but-inert affordance that invites a tap that does nothing, and no path by which the toddler's own hands can accidentally leave the drawing or leave the app.

## Screen Composition

The screen has two layers. Painting fills the entire screen as the drawing surface. Widgets are composed as chrome on top of it, anchored along the edges so a control never sits over the active drawing area and never requires reaching across the screen to a fixed toolbar band. User Experience owns which controls are present and how they're arranged relative to each other and to the drawing surface underneath; each control's own rendering, hit-testing, and activation belong to Widgets.

## Input Arbitration

At most one component's gesture is live on the whole screen at a time. User Experience achieves this with two mechanisms working together, rather than one central loop that manually classifies every touch: which of Widgets or Painting a fresh touch *reaches* is left to Compose's own pointer dispatch; whether the component it reached may act on it, and keeping every other component out for that gesture's duration, is decided by a single shared lock the children hold in turn.

**Routing.** Widgets is composed on top of Painting (see Screen Composition), and each does its own ordinary hit-testing on whatever pointer Compose delivers to it — Widgets via each control's own hit region (see the Widgets LLD's Hit-Testing and Activation), Painting via covering the full screen beneath. A touch inside some control's hit region goes to Widgets, a touch that misses every control falls through to Painting underneath, and whichever one receives it then asks the lock whether it may act on it. Layering settles which component a single pointer reaches; it doesn't settle a tie between two. Two pointers landing in the same input event, one on a control and one on the canvas, simply race for the lock, and which of them wins is left unspecified: exactly one starts a gesture and the other is refused, which is the only property arbitration needs. Picking a winner would mean overriding the toolkit's own dispatch to enforce an ordering no toddler could perceive. There's no attempt to guess intent and redirect an imprecise touch to a nearby control — a touch that misses becomes a canvas stroke rather than a discarded touch, even when the toddler's aim was probably a nearby control.

**The interaction lock.** User Experience creates one `InteractionLock` for the screen and hands it to every component that can start a gesture — Painting, and each Widgets control it composes. A component asks the lock for the interaction when its own gesture begins: the lock yields a hold when no one else has it, and refuses when someone does. Only the holder can end its own hold — acquiring returns a hold object, and releasing goes through that object rather than through the lock itself, so a component cannot release an interaction it never acquired, and a hold that has already been released can never free a later holder's. Releasing twice does nothing.

Each component asks once per gesture, from inside its own pointer-input loop, and releases in a `finally` covering that loop — so the hold ends on a clean finish, a failure, and a cancellation alike. A control whose action outlives the pointer that triggered it hands its hold to that action instead, which releases it when the work completes however it completes.

**When to ask.** A component asks only on an input event carrying a pointer newly touching down, and only when it isn't already holding the interaction. Both halves matter. A hovering pointer — moving with nothing pressed — carries no touch-down, so a pointer merely crossing the screen never takes the interaction, and a component that acquired on whatever event happened to arrive first would take it on hover and hold it for as long as its loop ran. The already-holding half is what lets a second finger join a gesture in progress without a second request: its component holds the interaction, so no question arises. Beyond not asking, a component leaves a hovering pointer entirely alone — neither consuming it nor treating it as part of a gesture — since it belongs to whatever handles hover, which today is nothing.

The mechanics are the component's own code rather than something the lock imposes, and that is a deliberate ceiling on how much this abstraction tries to do. Making acquire and release structurally unwritable — a combinator wrapping each gesture, or a pointer scope that arbitrates transparently on the way through — was explored and rejected; see Decisions & Alternatives.

Every acquire and release happens on the UI dispatcher, which is structural rather than incidental: Compose delivers pointer events there, so that's where a component asks; a holder releasing from its own pointer-input loop is already there; and a control releasing after its activation returns resumes on the dispatcher its composition-scoped coroutine started on, even if the activation itself moved to another one in between. The lock therefore needs no synchronization and holds no observable state — nothing renders from it. A component that acquired off the UI dispatcher would be breaking this invariant rather than extending it, and mutual exclusion would no longer hold.

The lock is ordinary screen state, created with `remember` and deliberately not `rememberSaveable`: a hold that outlived the composition would stand for a pointer that no longer exists, and nothing left alive could release it, so a restored screen always starts unheld. It's passed to each child explicitly rather than supplied ambiently, and a child requires one rather than defaulting to a private one of its own, so a component that was never wired into arbitration is a compile error instead of a silently unarbitrated control.

**Refusal.** A refused component starts nothing at all — no stroke, no press feedback, nothing on screen. The refusal lasts the whole gesture rather than a single event: a finger that touched down while another component held the interaction stays inert even if the holder releases while that finger is still down, and only a fresh touch-down afterwards is eligible to start anything. A hand already resting on the screen when an action began doesn't spring to life when it ends.

**Holding.** A hold excludes every *other* component and every other control, but says nothing about further pointers arriving at the holder itself — those are the holder's own to interpret, and the two children interpret them differently. Painting holds from the first pointer of a gesture touching down through the last one lifting, drawing every pointer that joins along the way (see the Painting LLD's Holding the Interaction). A Widgets control holds from the moment it claims a pointer through the end of whatever that pointer's release triggers: a release that activates nothing ends the hold immediately, while a release that activates keeps it until the activation's own work has finished, however long that runs (see the Widgets LLD's Interaction Arbitration Contract). Either way the release is unconditional on how the gesture ended: a cancelled gesture, or an activation that failed partway through, releases exactly as a clean completion does. No hold can outlive the gesture it covers, and no failure can leave the screen permanently unable to accept a touch.

Because a control takes the hold at claim rather than at activation, a Widgets action — including New Picture — can only start when no stroke is live on Painting, and there's no case where a lifecycle action fires mid-stroke. It also means New Picture's whole sequence runs under the hold its own press already took, with no gap at the release in between (see Lifecycle Behavior).

## Feature Gating

User Experience reads Config's resolved per-feature values (see the Config LLD's Resolved Features) — never the underlying age-slider value or custom toggle map directly — and uses them to decide which Widgets controls are composed onto the screen and which optional behaviors (such as whether OS back navigation is ever re-enabled — see OS Navigation and Process Lifecycle) are active. A feature that's off is omitted entirely rather than shown disabled: a visible-but-inert control invites a tap that does nothing, which the toddler-usability tenet treats as a broken interaction rather than a safe default.

Today the configuration gates the canvas feature set as a single bundle (color picker, New Picture) — there's no per-feature independence yet. Finer-grained gating is deferred until the feature set grows past what one bundle covers.

A resolved-feature change that arrives while a gesture is live (per Input Arbitration) doesn't recompose the screen immediately — the live gesture, including New Picture's own held sequence, finishes first, and the new composition applies starting with the next gesture. A control or color swatch never disappears out from under a pointer that's already down on it.

## Lifecycle Behavior

### New Picture

Triggered by New Picture's `onActivate` (see the Widgets LLD's Reporting Activation) — reachable, per Input Arbitration above, only when no stroke is active on Painting. The action runs a fixed sequence:

1. User Experience asks Painting whether the current drawing is empty. Painting owns this determination; User Experience owns what happens as a result.
2. If the drawing isn't empty, User Experience calls Painting's `save()` (see the Painting LLD), which writes the drawing to Image Storage. If it is empty, this step is skipped — no blank drawing is ever written.
3. Painting's canvas is cleared.

No confirmation dialog is shown, per the HLD's reversible-actions-default-to-forgiving tenet — the toddler can't parse or dismiss a confirmation prompt, and whenever there was content to lose, it's already recoverable because it was saved before the clear. The sequence doesn't surface an intermediate state that requires a response before drawing can resume.

The interaction hold that covers this sequence (see Input Arbitration) is already taken before the sequence even starts — New Picture acquired it the moment its pointer was claimed, not at `onActivate` — and it lasts through step 3 completing, including across the asynchronous `save()` call in step 2, rather than being released at the press's own release and re-acquired here. No new stroke or control-press can start anywhere in that window, from the initial claim through the sequence's end. This needs no special arrangement by User Experience beyond making the sequence the activation's own work: every Widgets control holds the interaction until its activation finishes, and for most controls that simply completes at once.

A finger resting on the canvas for the sequence's whole duration was refused at its own touch-down and stays refused (see Input Arbitration's Refusal), so it doesn't spring into a stroke the moment the sequence ends — the toddler lifts and touches again. That's the intended reading of the refusal rule rather than an exception to it: a hand already on the screen when an action started shouldn't start drawing on its own when the action finishes.

If the screen is recreated mid-sequence — a rotation, or backgrounding that recreates the composition — the sequence is cancelled where it stands and nothing resumes it. The intended outcome is that the toddler sees no effect at all: the drawing is still on the canvas when the screen returns, surviving by the ordinary mechanism (see OS Navigation and Process Lifecycle), exactly as if New Picture had never been pressed. The hold dies with the composition that owned it, so the returning screen starts unheld.

### OS Navigation and Process Lifecycle

The OS back gesture/button is consumed and ignored — it never navigates the toddler out of the kid canvas — at least under younger-age configurations; whether an older-age bundle ever re-enables it is deferred (see Feature Gating and Open Questions). This holds regardless of whether device-locking from the HLD's first-launch adult setup dialog is active — it's a baseline default on its own.

The current, in-progress drawing must survive any lifecycle event the OS handles through its own saved-instance-state mechanism — configuration changes, brief backgrounding, process death within that scope — the same category of survival Compose's `rememberSaveable` (or its Compose Multiplatform equivalent) provides for ordinary UI state. This is a distinct mechanism from the New Picture auto-save path above: routine OS lifecycle churn isn't a completed drawing worth writing to the permanent store, it's mid-work state that should simply still be there when the screen returns.

Whether device rotation specifically should be precluded altogether by locking screen orientation, rather than survived like any other configuration change, is an open question (see Open Questions).

## Interaction Feedback

Actions that User Experience orchestrates across components answer the toddler through the action's own visible effect, not through any separate dialog, confirmation, or extra interaction step:

- **Color selection** — Widgets owns the visual mechanism (e.g. which swatch shows as active); User Experience owns `StyleSettings`, the resolved brush and background source Painting reads from (see the Painting LLD) — color is a property of the brush instance `StyleSettings` resolves, not a separate value, so writing the toddler's swatch selection into `StyleSettings` means constructing a freshly colored brush instance for the next resolved-brush query. The next stroke Painting starts is simply in the new color, with no separate acknowledgment step required. Brush *type* has no selection input yet — `StyleSettings` always resolves an instance of Painting's single default brush type, just constructed with a color from a `ColorSource` (see the Painting Style LLD's Color Sources). The drawing surface's background is resolved the same way but has no selection input at all yet — no Widgets control writes into it (see the Painting LLD's Style Settings section for when Painting queries it).

  No swatch-tap wiring exists yet (Widgets has no implementation — see Open Questions), so today's `StyleSettings` implementation resolves both colors from fixed `ColorSource`s rather than anything a toddler's tap has chosen. The background is `ConstantColor(white)`. The stroke color is `RandomColor`, sampling a fresh color for every stroke: hue uniform across the full color wheel, saturation constant at `1.0`, and brightness sampled via a `PowerDistribution` biased well toward the bright end — a plain uniform or linear bias still produced visibly dark strokes often enough to look muddy, so brightness leans further toward bright than a uniform-over-the-color-wheel mapping would (see the Painting Style LLD's Distributions).
- **New Picture** — the cleared canvas is itself the feedback: the toddler sees the drawing surface go blank, confirming the action took effect. No separate confirmation banner or toast is shown, consistent with no blocking dialogs on the kid canvas.

Feedback belonging to a single control's own activation (a button's press animation, for example) is owned by Widgets, not here — this section covers only feedback for actions User Experience itself orchestrates across components.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Gated-off feature representation | Omit the control entirely | Show it disabled/greyed out | A disabled control invites a tap the toddler can't interpret the failure of — omission avoids a dead interaction rather than explaining one. |
| New Picture confirmation | None — auto-save-then-clear | Blocking confirmation dialog; clear-then-offer-undo toast | Direct application of the HLD's reversible-actions-default-to-forgiving tenet: the action is already recoverable via auto-save, so a confirmation step adds friction without adding safety. |
| Screen layering | Painting full-bleed as background; Widgets chrome anchored to the edges on top | Fixed non-overlapping regions (e.g. a dedicated toolbar strip above a smaller canvas area) | Maximizes the reachable drawing area and avoids losing screen real estate to a dedicated toolbar band, while edge anchoring keeps controls reachable without precise fine-motor reach. |
| Input arbitration between Widgets and Painting | Two mechanisms: ordinary Compose z-order dispatch decides which component receives a fresh touch (Widgets on top, Painting beneath); a shared `InteractionLock` each component takes for its own gesture's duration decides whether it may act on that touch | A transparent, pointer-consuming blocking layer the composition root raises over the whole screen while any gesture is live, driven by liveness callbacks from both children; a single hand-rolled arbiter that inspects every raw pointer itself and manually routes it to Widgets or Painting; per-touch heuristics to classify incidental vs. intentional touches; redirect an imprecise touch to the nearest control it probably meant to hit | Routing is already exactly what Compose's own hit-testing does for free when Widgets sits above Painting — reimplementing it by hand would just be a slower, bug-prone copy of the toolkit's own dispatch. Given that, a lock is the smaller addition of the two remaining options: refusal is decided by the component that actually owns the pointer, at the moment it would act, so the root keeps no liveness bookkeeping of its own and nothing has to be composed, re-composed, or correctly ordered to make blocking work. It also spans a gesture's full life more faithfully — a holder releases on cancellation as reliably as on a clean end, and a hold can outlast the pointer that took it, which a layer keyed on pointer liveness cannot express without the root re-asserting a signal it just cleared. |
| How a component tells the arbiter its gesture is live | It doesn't tell anyone — it takes the hold itself and keeps it for exactly as long as its gesture lasts | Each component reports liveness outward to the composition root (Widgets via `onPressedChange`, Painting via an `onStrokeActiveChange` mirror of it) and the root arbitrates on their behalf | The component that owns the pointer is the only one that knows its gesture's true span, including the cancellation paths a callback pair reports unreliably. Reporting liveness outward only to have the root decide something the reporter could decide itself adds a round trip and two boolean states in the root that can disagree with the pointers they describe. |
| Who may release a hold | Only whoever acquired it, through the hold object `tryAcquire` returns; the lock exposes no release of its own | A `release()` on the lock itself, callable by anyone; a caller-held identity token the lock checks on release | Releasing an interaction one never acquired is the failure worth designing out, not merely detecting: it hands the screen to a component mid-gesture and produces exactly the concurrent-pointer state arbitration exists to prevent. Routing release through the returned hold makes that unrepresentable rather than incorrect, and makes double-release and stale-hold release inert for the same reason. |
| Whether acquire and release are made structurally unwritable by components | No — each component acquires in its own pointer loop and releases in its own `finally` | A combinator wrapping each gesture block, owning acquire, release, and the refusal path around it; an arbitrating `AwaitPointerEventScope` that delegates to Compose's own and arbitrates transparently on every event, hiding refusals entirely and releasing by reference count | Both alternatives remove a real hazard — a component forgetting its release strands the screen — and both cost more than they save here. The wrapping combinator has to impose its own gesture boundary on the block it wraps, so the hold's span becomes "one block invocation" and stays correct only while each component's loop happens to exit exactly when its last pointer lifts. The transparent scope is not implementable at all: `AwaitPointerEventScope` carries Kotlin's `@RestrictsSuspension`, whose check is per-instance, so a delegating implementation cannot call through to the scope it wraps — meaning no wrapper can source pointer events. Arbitration through explicitly-named extension functions would work, but with two components and one acquire site each, the release is a `finally` away from the acquire and reviewable on sight. |
| Where `InteractionLock` lives | Owned by User Experience, alongside the Input Arbitration intent it implements; the screen constructs one and passes it to each child | A separate shared leaf both Widgets and Painting depend on, keeping children free of any dependency on the composition root; a `CompositionLocal` providing it ambiently; each child defaulting to a private lock when none is passed | The intent this type serves is already User Experience's and specified here, so a separate leaf would separate the mechanism from the intent that governs it, and split one small contract across two segments' specs. The resulting child-to-root reference is a source dependency within a single module, not a build cycle, and doesn't reintroduce any knowledge of Widgets in Painting or vice versa. Ambient provision and per-child defaults both turn a missing wiring into a silently unarbitrated control, where an explicit required parameter turns it into a compile error. |
| Auto-save on New Picture when the drawing is empty | Skipped — no save write, canvas still clears | Always auto-save regardless of content | Avoids cluttering the saved-drawings store with blank entries. Ownership stays split: Painting reports whether there's content, User Experience decides what that fact means. |
| OS back gesture | Consumed and ignored, at least under younger-age configurations | Standard OS back behavior (exits the app); mapping the gesture to an in-app action (e.g. New Picture) | A toddler navigating out of the app unsupervised is the failure mode the HLD's first-launch device-locking exists to prevent; ignoring back is a baseline defense independent of whether locking is active. Exact age cutoff, if any, is deferred. |
| Surviving OS-managed lifecycle events (rotation, brief backgrounding, saved-instance-state-scoped process death) | Current drawing persists via the platform's saved-instance-state mechanism, separate from the New Picture auto-save path | Rely on the New Picture auto-save path for this too; accept loss of in-progress work across these events | Routine OS churn isn't a completed drawing worth writing to the permanent store — it's ordinary transient UI state, no different from any other Compose screen's saved-instance-state handling — and shouldn't force a save-then-clear the toddler never asked for. |
| Ownership of `StyleSettings` (Painting's resolved brush and background source) | User Experience implements and owns it, writing the toddler's swatch selection into it as the color to construct the next resolved brush instance with (brush type has no selection input yet, so it always resolves an instance of Painting's single default type); the resolved background has no write path yet, so it's a fixed default | Painting owns an active brush directly as its own mutable state, written via a setter call from User Experience | Matches the Painting LLD's decision to keep Painting's stroke rendering ignorant of how a resolved brush gets decided. User Experience already owns Widgets' color-selection wiring, so it's the natural place to decide — and later evolve — what the resolved brush and background are. |
| New Picture's hold on the arbiter across its asynchronous save | Held continuously from the pointer's claim — before New Picture even activates — through `clear()` completing, spanning the `save()` call | Release the arbiter right after the press that claims it, re-acquiring it only once `onActivate` fires; release it right after `onActivate`, before `save()` begins | Painting's `save()` writes to Image Storage and isn't instant. Holding the interaction continuously, with no gap around the claim-to-activate window or the save call, means a touch made anywhere in that span is simply never accepted, rather than accepted as a new stroke and then invisibly erased a moment later by `clear()` — worse for a toddler than the touch just not registering. |
| Feature-gating change arriving during a live gesture | Applied only once the current gesture ends; never recomposes mid-gesture | Recompose immediately, mid-gesture, per Config's normal reactivity | A control or color swatch disappearing out from under a pointer already down on it is a worse toddler experience than a one-gesture-long delay in applying a parent's config change. |

## Open Questions & Future Decisions

### Resolved

1. ✅ User Experience observes UX-config changes live, not just at launch — Config exposes a reactive/observable read API. See the Config LLD's Reads Are Reactive section.
2. ✅ Painting is a hoisted-state Compose pattern owning its own pointer input, taking the interaction lock for its own gesture rather than reporting liveness back to User Experience — see the Painting LLD's Composable Shape and Holding the Interaction.
3. ✅ A resolved brush's color can change automatically between strokes, without a new toddler tap — today's stroke color source is `RandomColor`, sampling a fresh color every stroke. See Interaction Feedback and the Painting Style LLD's Color Sources.
4. ✅ A held interaction excludes every other component and every other control, while the holder's own concurrent pointers are the holder's own business to interpret — Painting draws all of them, a control ignores every one but the pointer it claimed. See Input Arbitration's Holding section.
5. ✅ `KidCanvasScreen` composes Widgets (New Picture) alongside Painting and owns the `InteractionLock` both of them take — see Screen Composition, Input Arbitration, and Lifecycle Behavior's New Picture section.

### Deferred

1. What happens if the auto-save on New Picture fails (storage full, write error)? Image Storage reports the failure to the caller, but what User Experience does in response is undefined — today's design assumes the save always succeeds before the canvas clears.
2. Per-feature gating granularity: once the feature set grows past the current single bundle, which features become independently toggle-able needs its own pass — including whether/at what age OS back navigation is ever re-enabled. Feature Gating itself has no implementation yet — Config's resolved-feature values aren't read anywhere in `KidCanvasScreen`, so every Widgets control it composes is unconditional.
3. Exact composition geometry — which edge each Widgets control anchors to, spacing, sizing — is deferred to implementation and visual design, not fixed here.
4. How `StyleSettings`' implementation constructs a correctly typed and colored brush instance once Painting Style supports more than one brush type is that LLD's own open question (see its Open Questions #4) — today's single-brush-type implementation just constructs that one type directly with a color from a `ColorSource`.
5. Ownership of the HLD's first-launch adult setup dialog (age slider, device-lock button, link into the Companion App, "don't show again" toggle) isn't assigned to any Kid Canvas component yet. User Experience, as the kid canvas's composition root, is the likely owner, but this LLD doesn't cover it — today's screen composition and lifecycle behavior are defined without it.
6. What resolved-feature values User Experience reads before Config's UX configuration has ever been written (first run, before any dialog or Companion App write) is Config's own default-resolution question, not decided here — see the Config LLD.
7. Color Picker has no implementation yet — `KidCanvasScreen` composes only New Picture today. Color selection's `StyleSettings` wiring (see Interaction Feedback) and OS back-gesture consumption (see OS Navigation and Process Lifecycle) are similarly unimplemented.
8. Whether the drawing surface's orientation should be locked to preclude live device rotation entirely, and if so, whether that lock applies unconditionally or is itself age-gated (see Feature Gating), isn't decided. The motivating concern is visual, not data-survival: rotating the canvas mid-session risks a jarring rotate-then-settle glitch a toddler-usability-first design would rather avoid than merely survive. `android:screenOrientation="locked"` — freezing to whichever orientation is active at launch rather than forcing a fixed portrait or landscape — is the leading candidate if this is pursued, since it defers to the user's own auto-rotate/manual-lock setting instead of overriding it. Rotation is left available for now, since it also exercises the same saved-instance-state survival path other configuration changes and process death use, which is otherwise harder to trigger for testing.
9. Arbitration handles hover only to the extent of staying out of its way: no component reacts to a hovering pointer today, so the guarantees stop at hover never taking the interaction and never being consumed as though it were part of a gesture (see Input Arbitration's When to ask). Giving a control a hover affordance needs three things revisited first. A refused gesture's drain consumes every event until no pointer is pressed, hover events included — even ones belonging to a different pointer with nothing to do with the refused press — so a hover affordance would go dead for the duration of someone else's refused touch, which is wrong. Widgets' hit-testing enters through Compose's `awaitFirstDown`, which returns only when *every* change in an event is a touch-down, so a pointer hovering a control while another touches it keeps that control from ever claiming the touch. And whether an `Exit` is delivered when a hovering pointer presses determines whether a hover affordance clears itself on press or has to be cleared explicitly. None of the three can arise on a touch-only device, so none is worth settling before a control actually wants hover. The hover behavior that *is* implemented — CANVAS-UX-027 and CANVAS-PAINT-024, which keep a hovering pointer from taking the interaction or reaching the drawing — rests on reading the code rather than on tests: the test harness injects touch, and a touch pointer is always pressed, so no test can produce a hovering one.
10. A New Picture sequence cancelled after its `save()` completed but before its `clear()` leaves the drawing on the canvas *and* a copy of it already in Image Storage; pressing New Picture again then writes a second entry for the same drawing. Today this is accepted rather than solved — the cost is one redundant entry in a gallery the parent can already delete from, in a race that needs a screen recreation to land inside the save window.

    Retaining the id `save()` returns, and passing it back to update that entry instead of creating another, is the obvious-looking fix and is not sufficient: the id doesn't exist until the write returns, cancellation is delivered at exactly that resumption, and the recreation's state snapshot can be captured before the write completes at all. It narrows the window to the write itself, which is nearly the whole sequence. Closing it properly means deciding a drawing's identity *before* the write — a caller-supplied key that a create-or-update-by-key operation matches on — which Image Storage's current data shape rules out (ids are storage-minted and never caller-invented, and MediaStore assigns its own row id), so it would need a separate key field and a uniqueness rule of its own.
