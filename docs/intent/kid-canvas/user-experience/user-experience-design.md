# User Experience

## Context and Design Philosophy

User Experience is Kid Canvas's composition root: it arranges Widgets (buttons, color picker, and similar chrome) and Painting (the drawing surface) into one screen, and owns whatever behavior belongs to the screen as a whole rather than to either child on its own — which controls are present, what happens when a lifecycle action fires, how touches are arbitrated between drawing and chrome, and how the screen answers a toddler's action immediately. Widgets and Painting don't depend on each other; User Experience is the only component that depends on both. The one thing they take back from User Experience is the interaction lock defined here (see Input Arbitration) — the arbiter each of them holds in turn, and the only channel through which either learns that some *other* gesture is live, without learning whose.

The toddler-usability tenet governs every decision here: no confirmation dialogs, no state a toddler has to interpret before continuing, no visible-but-inert affordance that invites a tap that does nothing, and no path by which the toddler's own hands can accidentally leave the drawing or leave the app.

## Screen Composition

The screen has two standing layers. Painting fills the entire screen as the drawing surface. Widgets are composed as chrome on top of it, anchored along the edges so a control never sits over the active drawing area and never requires reaching across the screen to a fixed toolbar band. User Experience owns which controls are present and how they're arranged relative to each other and to the drawing surface underneath; each control's own rendering, hit-testing, and activation belong to Widgets.

A third layer exists only while User Experience is showing something of its own — today, the save feedback in Putting the Drawing Away — and sits between those two, over the drawing area and beneath the chrome. It's presentation rather than structure: it belongs to no control, accepts no input, and never outlives the action that raised it. The rule that no *control* sits over the drawing area is untouched by it.

## Input Arbitration

At most one component's gesture is live on the whole screen at a time. User Experience achieves this with two mechanisms working together, rather than one central loop that manually classifies every touch: which of Widgets or Painting a fresh touch *reaches* is left to Compose's own pointer dispatch; whether the component it reached may act on it, and keeping every other component out for that gesture's duration, is decided by a single shared lock the children hold in turn.

**Routing.** Widgets is composed on top of Painting (see Screen Composition), and each does its own ordinary hit-testing on whatever pointer Compose delivers to it — Widgets via each control's own hit region (see the Widgets LLD's Hit-Testing and Activation), Painting via covering the full screen beneath. A touch inside some control's hit region goes to Widgets, a touch that misses every control falls through to Painting underneath, and whichever one receives it then asks the lock whether it may act on it. Layering settles which component a single pointer reaches; it doesn't settle a tie between two. Two pointers landing in the same input event, one on a control and one on the canvas, simply race for the lock, and which of them wins is left unspecified: exactly one starts a gesture and the other is refused, which is the only property arbitration needs. Picking a winner would mean overriding the toolkit's own dispatch to enforce an ordering no toddler could perceive. There's no attempt to guess intent and redirect an imprecise touch to a nearby control — a touch that misses becomes a canvas stroke rather than a discarded touch, even when the toddler's aim was probably a nearby control.

**The interaction lock.** User Experience creates one `InteractionLock` for the screen and hands it to every component that can start a gesture — Painting, and each Widgets control it composes. A component asks the lock for the interaction when its own gesture begins: the lock yields a hold when no one else has it, and refuses when someone does. Only the holder can end its own hold — acquiring returns a hold object, and releasing goes through that object rather than through the lock itself, so a component cannot release an interaction it never acquired, and a hold that has already been released can never free a later holder's. Releasing twice does nothing.

Each component asks once per gesture, from inside its own pointer-input loop, and releases in a `finally` covering that loop — so the hold ends on a clean finish, a failure, and a cancellation alike. A control whose action outlives the pointer that triggered it hands its hold to that action instead, which releases it when the work completes however it completes.

**When to ask.** A component asks only on an input event carrying a pointer newly touching down, and only when it isn't already holding the interaction. Both halves matter. A hovering pointer — moving with nothing pressed — carries no touch-down, so a pointer merely crossing the screen never takes the interaction, and a component that acquired on whatever event happened to arrive first would take it on hover and hold it for as long as its loop ran. The already-holding half is what lets a second finger join a gesture in progress without a second request: its component holds the interaction, so no question arises. Beyond not asking, a component leaves a hovering pointer entirely alone — neither consuming it nor treating it as part of a gesture — since it belongs to whatever handles hover, which today is nothing.

The mechanics are the component's own code rather than something the lock imposes, and that is a deliberate ceiling on how much this abstraction tries to do. Making acquire and release structurally unwritable — a combinator wrapping each gesture, or a pointer scope that arbitrates transparently on the way through — was explored and rejected; see Decisions & Alternatives.

Every acquire and release happens on the UI dispatcher, which is structural rather than incidental: Compose delivers pointer events there, so that's where a component asks; a holder releasing from its own pointer-input loop is already there; and a control releasing after its activation returns resumes on the dispatcher its composition-scoped coroutine started on, even if the activation itself moved to another one in between. The lock therefore needs no synchronization and holds no observable state — nothing renders from it. A component that acquired off the UI dispatcher would be breaking this invariant rather than extending it, and mutual exclusion would no longer hold.

The lock is ordinary screen state, created with `remember` and deliberately not `rememberSaveable`: a hold that outlived the composition would stand for a pointer that no longer exists, and nothing left alive could release it, so a restored screen always starts unheld. It's passed to each child explicitly rather than supplied ambiently, and a child requires one rather than defaulting to a private one of its own, so a component that was never wired into arbitration is a compile error instead of a silently unarbitrated control.

**Refusal.** A refused component starts nothing at all — no stroke, no press feedback, nothing on screen. The refusal lasts the whole gesture rather than a single event: a finger that touched down while another component held the interaction stays inert even if the holder releases while that finger is still down, and only a fresh touch-down afterwards is eligible to start anything. A hand already resting on the screen when an action began doesn't spring to life when it ends.

**Holding.** A hold excludes every *other* component and every other control, but says nothing about further pointers arriving at the holder itself — those are the holder's own to interpret, and the two children interpret them differently. Painting holds from the first pointer of a gesture touching down through the last one lifting, drawing every pointer that joins along the way (see the Painting LLD's Holding the Interaction). A Widgets control holds from the moment it claims a pointer through the end of whatever that pointer's release triggers: a release that activates nothing ends the hold immediately, while a release that activates keeps it until the activation's own work has finished, however long that runs (see the Widgets LLD's Interaction Arbitration Contract). Either way the release is unconditional on how the gesture ended: a cancelled gesture, or an activation that failed partway through, releases exactly as a clean completion does. No hold can outlive the gesture it covers, and no failure can leave the screen permanently unable to accept a touch.

Because a control takes the hold at claim rather than at activation, a Widgets action — including New Picture — can only start when no stroke is live on Painting, and there's no case where a lifecycle action fires mid-stroke. It also means New Picture's whole sequence runs under the hold its own press already took, with no gap at the release in between (see Lifecycle Behavior).

## Feature Gating

User Experience reads Config's resolved per-feature values (see the Config LLD's Resolved Features) — never the underlying age-slider value or custom toggle map directly — and uses them to decide which Widgets controls are composed onto the screen and which optional behaviors (such as whether OS back navigation is ever re-enabled — see OS Navigation and Process Lifecycle) are active. A feature that's off is omitted entirely rather than shown disabled: a visible-but-inert control invites a tap that does nothing, which the toddler-usability tenet treats as a broken interaction rather than a safe default.

Today the configuration gates the canvas feature set as a single bundle (color picker, New Picture) — there's no per-feature independence yet. Finer-grained gating is deferred until the feature set grows past what one bundle covers.

A resolved-feature change that arrives while a gesture is live (per Input Arbitration) doesn't recompose the screen immediately — the live gesture, including New Picture's own held sequence, finishes first, and the new composition applies starting with the next gesture. A control or color swatch never disappears out from under a pointer that's already down on it.

## Lifecycle Behavior

### New Picture

Triggered by New Picture's `onActivate` (see the Widgets LLD's Reporting Activation) — reachable, per Input Arbitration above, only when no stroke is active on Painting. The action runs a fixed sequence:

1. User Experience asks Painting whether the current drawing is empty. Painting owns this determination; User Experience owns what happens as a result.
2. If the drawing isn't empty, User Experience takes a snapshot of it — a still image of the drawing as it stands — and calls Painting's `save()` (see the Painting LLD), which writes the drawing to Image Storage. If that call reports a failure, it calls `save()` once more; if the second call fails too, the sequence ends here. If the drawing is empty, the whole step is skipped — neither snapshot nor save — and no blank drawing is ever written.
3. Painting's canvas is cleared.

The snapshot in step 2 is what the toddler then watches leave, or fail to leave; a save that succeeds takes a second one after step 3, of the cleared canvas, as the fresh sheet that arrives in its place. See Putting the Drawing Away below. An empty drawing skips all of it along with the save — there was nothing to put away and nothing to replace.

No confirmation dialog is shown, per the HLD's reversible-actions-default-to-forgiving tenet — the toddler can't parse or dismiss a confirmation prompt, and whenever there was content to lose, it's already recoverable because it was saved before the clear. The sequence doesn't surface an intermediate state that requires a response before drawing can resume.

The clear is conditional on the save for that same reason. A clear that ran after a failed save would destroy a drawing with nothing left to recover it from — the one outcome the forgiving-by-default tenet rules out, and the outcome the absence of a confirmation step assumes can't happen. So a drawing that couldn't be saved stays on the canvas.

The retry is immediate, has no backoff, and happens exactly once. One repeat covers a transient I/O error, the failure most likely to resolve on a second attempt; a storage-full condition won't clear on its own, and a toddler holding the screen while retries accumulate is worse than the action simply not taking effect.

Repeating the save blindly is safe only because a failed write leaves nothing behind: Image Storage removes a partially created entry before reporting the failure (see the Image Storage LLD's Write Failures), so the second attempt writes the drawing once rather than a second time. That guarantee is what this retry rests on. A failure carries no indication of how far the first attempt got, so without it the retry would have to assume it might be duplicating the drawing and could do nothing about it either way.

The interaction hold that covers this sequence (see Input Arbitration) is already taken before the sequence even starts — New Picture acquired it the moment its pointer was claimed, not at `onActivate` — and it lasts until the sequence ends, including across the asynchronous `save()` call and any retry in step 2, rather than being released at the press's own release and re-acquired here. That covers a sequence that ends early on a failed save exactly as it covers one that reaches the clear: the hold ends with the activation's own work, whatever that work concluded. No new stroke or control-press can start anywhere in that window, from the initial claim through the sequence's end. This needs no special arrangement by User Experience beyond making the sequence the activation's own work: every Widgets control holds the interaction until its activation finishes, and for most controls that simply completes at once.

A finger resting on the canvas for the sequence's whole duration was refused at its own touch-down and stays refused (see Input Arbitration's Refusal), so it doesn't spring into a stroke the moment the sequence ends — the toddler lifts and touches again. That's the intended reading of the refusal rule rather than an exception to it: a hand already on the screen when an action started shouldn't start drawing on its own when the action finishes.

If the screen is recreated mid-sequence — a rotation, or backgrounding that recreates the composition — the sequence is cancelled where it stands and nothing resumes it. The intended outcome is that the toddler sees no effect at all: the drawing is still on the canvas when the screen returns, surviving by the ordinary mechanism (see OS Navigation and Process Lifecycle), exactly as if New Picture had never been pressed. The hold dies with the composition that owned it, so the returning screen starts unheld.

### Putting the Drawing Away

The sequence above decides what happens to the drawing; this decides what the toddler sees happen to it. A press that saved and a press that couldn't save must not look alike, and neither may be a message to read or a prompt to dismiss — the toddler can't read, and the HLD rules out any dialog shown in response to something the toddler did.

The drawing itself carries the answer, in two movements. Both animate the step 2 snapshot, laid over the screen at exactly the size and position the drawing occupied, so the first frame is indistinguishable from the canvas it replaces.

**Picking it up.** The snapshot first shrinks where it stands, until it is small enough that it no longer reaches the button, and then crosses to rest at the button, overlapping its top edge slightly and drawn *over* it. The order is what makes both parts possible: a sheet still filling the screen cannot be drawn over the button without taking it off screen entirely, so it has to shrink clear before it can come forward. This says only that the drawing has been picked up, which is true the moment the toddler's finger lifts — so it starts immediately, without waiting to learn whether the write succeeded. That matters for how the action feels: the write is not instant, and a sequence that waits for it before moving leaves a gap between the press ending and anything happening, which reads as a stall. If the write is still running when the lift finishes, the snapshot simply waits where it is. A drawing held over the slot is a pose the action already has a use for, rather than a spinner invented to fill time.

**Putting it down.** Every change of layer in the sequence falls where the sheet doesn't overlap the button, so none of them can be seen — and each outcome gets that moment from a movement it wanted anyway:

- **Saved** — the sheet hops up clear of the button, then descends into it from there, now behind it, so the button swallows it as it goes. A drawing that goes somewhere reads as put away; one that merely vanishes, or that exits toward nothing at the screen's edge, reads as thrown out, which is the opposite of what happened. Then a fresh sheet arrives to replace it, along the departing drawing's own path in reverse: in from off screen on the far side from the button, to the same shrunk, centred spot a leaving sheet passes through, and out from there until it fills the screen. Running the exchange through one place makes the two sheets read as replacing each other rather than as two unrelated things moving; entering from wholly off screen, opposite the side the old one left by, is what makes it an arrival rather than a zoom. So a new picture is something the toddler watches show up, not something that was simply already there.
- **Not saved** — the sheet simply goes back the way it came: away from the button to where it last cleared it, then growing to full size, ending exactly where it started. It needs no hop, because retracing its own path clears the button on its own — and a drawing that failed to go anywhere should look like it turned back, not like it was set down deliberately. No fresh sheet arrives, because nothing was taken away. A red flash bursts from the button at the turn, expanding to fill the screen as it brightens and fades, so color and motion say the same thing at the same moment and both say it comes from the thing that was pressed. The rebound isn't a decoration laid over the failure: the drawing genuinely is still on the canvas afterwards, and this is that fact in motion.

Underneath all of this the canvas is covered by a plain white field, from the moment the drawing is picked up until the sequence ends. The cover is not standing in for the canvas — it's the bare surface between two sheets, which is why it can be white whatever color the next drawing's background turns out to be. That's what makes the arriving sheet worth animating rather than merely revealing: a background resolved by `clear()` shows up *on* the sheet that carries it, at the moment that sheet arrives, instead of appearing unannounced when a cover lifts.

Painting's canvas is cleared as soon as the save reports success, while the drawing is still being lifted — the clear commits at the same point in the sequence it always did, and the flight stays presentation laid over a sequence that has already finished. The arriving sheet is a second snapshot, taken after that clear, so it carries exactly what the real canvas now shows; when it lands at full size the cover comes off beneath it and the live canvas takes over without a seam.

Both sheets carry a border while they move. Without one each is a near-white sheet over a near-white surface, and only the strokes would appear to travel; the border is what makes it read as a single piece of paper rather than a drawing dissolving or condensing. Wherever a sheet comes to rest at full size — the rebound on the failed path, the arriving sheet on the saved one — the border has to be gone by the time it lands, because that final frame is the one the live canvas is handed back through, and a border still on it would flicker off.

Neither snapshot requires User Experience to know what color anything is. `clear()` deliberately resolves a *fresh* background, and User Experience has no way to ask what that would be without consuming a value from the source that produces it — so it doesn't ask. It photographs the canvas after the clear instead, and the color arrives in the picture.

The flight is the activation's own work, so the interaction hold covers it (see Input Arbitration's Holding). No other gesture can start while the snapshot is in motion, and the snapshot takes no pointer input of its own — it can't be grabbed, redirected, or chased under the button. The New Picture button stays the only thing on screen there is to press, and pressing it does what it always does.

Two consequences of that hold are worth naming rather than leaving to be rediscovered. The window in which a touch is refused and stays refused (see Input Arbitration's Refusal) now spans the flight as well as the save, so a toddler who puts a finger down while the drawing is travelling has to lift it and touch again before that finger can draw. That's the existing rule over a longer window, not a new one, and it's the right trade: a finger resting through the flight shouldn't spring into a stroke the moment the canvas settles. And the New Picture button is in its resting state throughout, because press feedback ends with the press — the button answers the finger, not the save. Whether it should also react as the drawing arrives under it is Widgets' to decide (see Open Questions).

An empty canvas skips all of this, because nothing was put away. The press is still answered, by the button's own press feedback — which is Widgets' to own, not this section's (see the Widgets LLD) — and a canvas that already looked blank stays blank. This is the one press that leaves the drawing surface showing nothing at all, and it's meant to: a sequence that wrote nothing has nothing to acknowledge, and inventing an acknowledgment for it would say a drawing was put away when none was.

If the screen is recreated mid-flight, the animation is abandoned along with the rest of the sequence and nothing resumes it. The snapshot is presentation only and nothing restores it, so the returning screen shows the sequence's committed result with no animation around it: a cleared canvas if the save landed, the drawing untouched if it didn't. Neither is a state the sequence couldn't already reach — the recreation costs the flight, not the outcome.

Where the platform reports that the user has asked for reduced motion, the flight doesn't run, and no snapshot is taken — nothing would display it, and rasterizing a full screen to discard it is the one part of this that isn't free. A saved drawing then leaves a cleared canvas behind and nothing else, which is acknowledgment enough for the outcome that has one; a failed save shows the red flash, standing alone. The flash is what makes that fallback viable — without it, a failed save under reduced motion would again be indistinguishable from a press that never registered, which is the gap this section exists to close. The preference reaches the screen as a value passed in, alongside the `ImageStorage` and the `InteractionLock` it already takes, rather than being queried from the platform where it's used, and is read once when the sequence reaches its feedback, so a preference that changes mid-flight never applies to half of one. Which platform signal feeds it, and how each platform sources one, isn't settled here — but a screen that reads the platform inline can't be shown either state by a test, and the reduced-motion path is the one where a failed save has the least left to say. No platform supplies it yet: every caller passes false today, so a device that has asked for reduced motion still gets the full flight (see Open Questions).

Duration and easing aren't fixed here: fast enough never to feel like waiting, slow enough to be seen. One thing about them is intent rather than taste, though. Movements the toddler should read as a single gesture — shrinking and then crossing to the button, or turning back and then growing home — are split into two only because the layer changes between them; nothing about them is meant to look like two movements. Their easings therefore have to hand off with speed still on: the first accelerates and ends moving, the second takes that speed up and slows into place. Giving each the usual curve that starts and ends at rest puts a standstill in the middle of one gesture, which is exactly what the split was supposed to be invisible about. The motion is translation and scale, which is a floor rather than the intent — see Open Questions.

The flash's own treatment is left to visual design with one constraint: strokes are colored from the full hue wheel (see Interaction Feedback), so a red flash will sometimes fall over a drawing that is already substantially red, and it has to stay legible there rather than only against a pale canvas.

### OS Navigation and Process Lifecycle

The OS back gesture/button is consumed and ignored — it never navigates the toddler out of the kid canvas — at least under younger-age configurations; whether an older-age bundle ever re-enables it is deferred (see Feature Gating and Open Questions). This holds regardless of whether device-locking from the HLD's first-launch adult setup dialog is active — it's a baseline default on its own.

The current, in-progress drawing must survive any lifecycle event the OS handles through its own saved-instance-state mechanism — configuration changes, brief backgrounding, process death within that scope — the same category of survival Compose's `rememberSaveable` (or its Compose Multiplatform equivalent) provides for ordinary UI state. This is a distinct mechanism from the New Picture auto-save path above: routine OS lifecycle churn isn't a completed drawing worth writing to the permanent store, it's mid-work state that should simply still be there when the screen returns.

Whether device rotation specifically should be precluded altogether by locking screen orientation, rather than survived like any other configuration change, is an open question (see Open Questions).

## Interaction Feedback

Actions that User Experience orchestrates across components answer the toddler through the action's own visible effect, not through any separate dialog, confirmation, or extra interaction step:

- **Color selection** — Widgets owns the visual mechanism (e.g. which swatch shows as active); User Experience owns `StyleSettings`, the resolved brush and background source Painting reads from (see the Painting LLD) — color is a property of the brush instance `StyleSettings` resolves, not a separate value, so writing the toddler's swatch selection into `StyleSettings` means constructing a freshly colored brush instance for the next resolved-brush query. The next stroke Painting starts is simply in the new color, with no separate acknowledgment step required. Brush *type* has no selection input yet — `StyleSettings` always resolves an instance of Painting's single default brush type, just constructed with a color from a `ColorSource` (see the Painting Style LLD's Color Sources). The drawing surface's background is resolved the same way but has no selection input at all yet — no Widgets control writes into it (see the Painting LLD's Style Settings section for when Painting queries it).

  No swatch-tap wiring exists yet (Widgets has no implementation — see Open Questions), so today's `StyleSettings` implementation resolves both colors from fixed `ColorSource`s rather than anything a toddler's tap has chosen. The background is `ConstantColor(white)`. The stroke color is `RandomColor`, sampling a fresh color for every stroke: hue uniform across the full color wheel, saturation constant at `1.0`, and brightness sampled via a `PowerDistribution` biased well toward the bright end — a plain uniform or linear bias still produced visibly dark strokes often enough to look muddy, so brightness leans further toward bright than a uniform-over-the-color-wheel mapping would (see the Painting Style LLD's Distributions).
- **New Picture** — the drawing's own motion is the feedback: it travels under the New Picture button when it was saved, and springs back to full size under a red flash when it couldn't be, so the two outcomes don't look alike and neither looks like a press that never registered. See Lifecycle Behavior's Putting the Drawing Away. No banner, toast, or text accompanies either — the toddler can't read one, and nothing appears that has to be dismissed.

Feedback belonging to a single control's own activation (a button's press animation, for example) is owned by Widgets, not here — this section covers only feedback for actions User Experience itself orchestrates across components.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Gated-off feature representation | Omit the control entirely | Show it disabled/greyed out | A disabled control invites a tap the toddler can't interpret the failure of — omission avoids a dead interaction rather than explaining one. |
| New Picture confirmation | None — auto-save-then-clear | Blocking confirmation dialog; clear-then-offer-undo toast | Direct application of the HLD's reversible-actions-default-to-forgiving tenet: the action is already recoverable via auto-save, so a confirmation step adds friction without adding safety. |
| Screen layering | Painting full-bleed as background; Widgets chrome anchored to the edges on top | Fixed non-overlapping regions (e.g. a dedicated toolbar strip above a smaller canvas area) | Maximizes the reachable drawing area and avoids losing screen real estate to a dedicated toolbar band, while edge anchoring keeps controls reachable without precise fine-motor reach. |
| Input arbitration between Widgets and Painting | Two mechanisms: ordinary Compose z-order dispatch decides which component receives a fresh touch (Widgets on top, Painting beneath); a shared `InteractionLock` each component takes for its own gesture's duration decides whether it may act on that touch | A transparent, pointer-consuming blocking layer the composition root raises over the whole screen while any gesture is live, driven by liveness callbacks from both children; a single hand-rolled arbiter that inspects every raw pointer itself and manually routes it to Widgets or Painting; per-touch heuristics to classify incidental vs. intentional touches; redirect an imprecise touch to the nearest control it probably meant to hit | Routing is already exactly what Compose's own hit-testing does for free when Widgets sits above Painting — reimplementing it by hand would just be a slower, bug-prone copy of the toolkit's own dispatch. Given that, a lock is the smaller addition of the two remaining options: refusal is decided by the component that actually owns the pointer, at the moment it would act, so the root keeps no liveness bookkeeping of its own and nothing has to be composed, re-composed, or correctly ordered to make blocking work. It also spans a gesture's full life more faithfully — a holder releases on cancellation as reliably as on a clean end, and a hold can outlast the pointer that took it, which a layer keyed on pointer liveness cannot express without the root re-asserting a signal it just cleared. |
| How a component tells the arbiter its gesture is live | It doesn't tell anyone — it takes the hold itself and keeps it for exactly as long as its gesture lasts | Each component reports liveness outward to the composition root (Widgets via `onPressedChange`, Painting via an `onStrokeActiveChange` mirror of it) and the root arbitrates on their behalf | The component that owns the pointer is the only one that knows its gesture's true span, including the cancellation paths a callback pair reports unreliably. Reporting liveness outward only to have the root decide something the reporter could decide itself adds a round trip and two boolean states in the root that can disagree with the pointers they describe. |
| Who may release a hold | Only whoever acquired it, through the hold object `tryAcquire` returns; the lock exposes no release of its own | A `release()` on the lock itself, callable by anyone; a caller-held identity token the lock checks on release | Releasing an interaction one never acquired is the failure worth designing out, not merely detecting: it hands the screen to a component mid-gesture and produces exactly the concurrent-pointer state arbitration exists to prevent. Routing release through the returned hold makes that unrepresentable rather than incorrect, and makes double-release and stale-hold release inert for the same reason. |
| Whether acquire and release are made structurally unwritable by components | No — each component acquires in its own pointer loop and releases in its own `finally` | A combinator wrapping each gesture block, owning acquire, release, and the refusal path around it; an arbitrating `AwaitPointerEventScope` that delegates to Compose's own and arbitrates transparently on every event, hiding refusals entirely and releasing by reference count | Both alternatives remove a real hazard — a component forgetting its release strands the screen — and both cost more than they save here. The wrapping combinator has to impose its own gesture boundary on the block it wraps, so the hold's span becomes "one block invocation" and stays correct only while each component's loop happens to exit exactly when its last pointer lifts. The transparent scope is not implementable at all: `AwaitPointerEventScope` carries Kotlin's `@RestrictsSuspension`, whose check is per-instance, so a delegating implementation cannot call through to the scope it wraps — meaning no wrapper can source pointer events. Arbitration through explicitly-named extension functions would work, but with two components and one acquire site each, the release is a `finally` away from the acquire and reviewable on sight. |
| Where `InteractionLock` lives | Owned by User Experience, alongside the Input Arbitration intent it implements; the screen constructs one and passes it to each child | A separate shared leaf both Widgets and Painting depend on, keeping children free of any dependency on the composition root; a `CompositionLocal` providing it ambiently; each child defaulting to a private lock when none is passed | The intent this type serves is already User Experience's and specified here, so a separate leaf would separate the mechanism from the intent that governs it, and split one small contract across two segments' specs. The resulting child-to-root reference is a source dependency within a single module, not a build cycle, and doesn't reintroduce any knowledge of Widgets in Painting or vice versa. Ambient provision and per-child defaults both turn a missing wiring into a silently unarbitrated control, where an explicit required parameter turns it into a compile error. |
| Auto-save on New Picture when the drawing is empty | Skipped — no save write, canvas still clears | Always auto-save regardless of content | Avoids cluttering the saved-drawings store with blank entries. Ownership stays split: Painting reports whether there's content, User Experience decides what that fact means. |
| New Picture when the auto-save fails | One immediate retry; if that fails too, the sequence ends without clearing and the drawing stays on the canvas | Clear regardless of the save's outcome; skip the clear with no retry at all; retry repeatedly with backoff until it succeeds; surface the failure to the toddler and let them choose | Clearing after a failed save is the only path in the whole design that can destroy a drawing unrecoverably, and the no-confirmation-dialog decision above is justified on the premise that it can't happen — so the clear has to be conditional on the save. One retry is worth having because a transient I/O error is a real and self-resolving failure; unbounded retries are not, because the failure that actually motivates this (storage full) never resolves on its own and would hold the interaction indefinitely while the toddler waits. Asking the toddler to choose is ruled out by the toddler-usability tenet for the same reason a confirmation dialog is. |
| OS back gesture | Consumed and ignored, at least under younger-age configurations | Standard OS back behavior (exits the app); mapping the gesture to an in-app action (e.g. New Picture) | A toddler navigating out of the app unsupervised is the failure mode the HLD's first-launch device-locking exists to prevent; ignoring back is a baseline defense independent of whether locking is active. Exact age cutoff, if any, is deferred. |
| Surviving OS-managed lifecycle events (rotation, brief backgrounding, saved-instance-state-scoped process death) | Current drawing persists via the platform's saved-instance-state mechanism, separate from the New Picture auto-save path | Rely on the New Picture auto-save path for this too; accept loss of in-progress work across these events | Routine OS churn isn't a completed drawing worth writing to the permanent store — it's ordinary transient UI state, no different from any other Compose screen's saved-instance-state handling — and shouldn't force a save-then-clear the toddler never asked for. |
| Ownership of `StyleSettings` (Painting's resolved brush and background source) | User Experience implements and owns it, writing the toddler's swatch selection into it as the color to construct the next resolved brush instance with (brush type has no selection input yet, so it always resolves an instance of Painting's single default type); the resolved background has no write path yet, so it's a fixed default | Painting owns an active brush directly as its own mutable state, written via a setter call from User Experience | Matches the Painting LLD's decision to keep Painting's stroke rendering ignorant of how a resolved brush gets decided. User Experience already owns Widgets' color-selection wiring, so it's the natural place to decide — and later evolve — what the resolved brush and background are. |
| New Picture's hold on the arbiter across its asynchronous save | Held continuously from the pointer's claim — before New Picture even activates — through `clear()` completing, spanning the `save()` call | Release the arbiter right after the press that claims it, re-acquiring it only once `onActivate` fires; release it right after `onActivate`, before `save()` begins | Painting's `save()` writes to Image Storage and isn't instant. Holding the interaction continuously, with no gap around the claim-to-activate window or the save call, means a touch made anywhere in that span is simply never accepted, rather than accepted as a new stroke and then invisibly erased a moment later by `clear()` — worse for a toddler than the touch just not registering. |
| Feature-gating change arriving during a live gesture | Applied only once the current gesture ends; never recomposes mid-gesture | Recompose immediately, mid-gesture, per Config's normal reactivity | A control or color swatch disappearing out from under a pointer already down on it is a worse toddler experience than a one-gesture-long delay in applying a parent's config change. |
| What New Picture shows for a save and for a failed save | The drawing's own motion — under the button when saved, a rebound to full size when not | The cleared canvas alone as the only acknowledgment, with a failed save showing nothing; a banner, toast, or icon; a sound instead of a visual | The cleared canvas can only speak for the outcome where there is one — a failed save clears nothing, so it looks exactly like a press that never registered, which is the failure the toddler-usability tenet treats as broken. Anything textual is unreadable to a pre-literate toddler and, if dismissible, is the dialog the HLD forbids in response to something the toddler did. Moving the drawing needs no vocabulary to learn: the object that changed is the object that moves. Sound isn't ruled out as an addition, but can't carry this alone — the device may be muted, and a toddler may not connect a sound to a picture. |
| Where the drawing goes | Under the New Picture button — the control that was pressed | A folder or other container drawn on the canvas; a stack of sheets beside the button; off the screen's edge toward no destination at all | Direction is what separates *kept* from *discarded*: a drawing exiting toward nothing is how a deletion would be animated. A destination must therefore exist, and the pressed control is the only one already on screen. It adds no chrome, no metaphor to decode — a folder is an office object a toddler has never seen — and no new shape inviting a tap it can't answer, since it is already a control that behaves correctly when tapped. Passing *under* it, which the existing Widgets-over-Painting layering gives for free, reads as stored rather than consumed. A stack of sheets is the upgrade if the button ever reads as eating the picture; it reuses the same flight and is purely additive. |
| When the motion starts relative to the save | Immediately, in two movements: an outcome-independent lift, then a resolution once the write returns | Wait for the outcome and play one movement; start the whole thing optimistically and reverse it on failure | The write is not instant, and nothing else covers it — the button's press feedback ends with the finger that caused it, so a sequence that waits reads as a stall between the press ending and anything happening. Splitting the motion removes the wait without ever depicting an outcome that hasn't happened: being picked up is true the moment the finger lifts. A drawing held above the button is also a pose the action already has a use for, so a slow write degrades into waiting-to-be-filed rather than a frozen screen or an invented spinner. A wholly optimistic flight would instead have to un-commit a clear it had already shown. |
| What lies behind the travelling snapshot | A plain white field, for the sequence's whole duration on both paths | Reveal the real canvas as soon as the clear commits; have Painting expose a muted mode rendering its own resolved background and none of its strokes | Once the arriving sheet carries its own background, the cover no longer stands in for the canvas — it's the bare surface between two sheets, and can be white whatever the next background turns out to be. Revealing the real canvas early would put an unannounced color change on screen the moment the cover lifted; sourcing the cover from Painting would buy an accuracy that a surface deliberately *not* pretending to be the canvas has no use for. |
| How the new canvas appears | A second snapshot, taken after the clear, that turns and slides into place | Simply reveal the cleared canvas when the cover lifts; transform the live Painting composable into place instead of a snapshot | A new picture arriving is the outcome worth showing — and it's the only place the freshly resolved background can appear without seeming to change on its own. Photographing the canvas after the clear also gets that color without asking `StyleSettings` for it, which would consume a value from the source that produces it. Transforming Painting itself would save a rasterization but requires lifting the cover first, leaving whatever sits behind Painting visible around the moving sheet instead of a surface. |
| Layering of the travelling snapshot relative to the button | Over the button while it is at the button, beneath it otherwise, with every change of layer placed where the two do not overlap | Beneath the button throughout; over it throughout; switching layer whenever the movement changes, wherever that falls | A sheet still filling the screen cannot be drawn over the button without hiding it, and a sheet that only ever passes behind never reads as coming forward to the slot at all. Both are avoidable because the movement can be shaped to suit: shrinking in place before crossing, and retracing that path on the way back, each pass through a moment of no overlap where the layer can change unseen. Only the descent lacks one of its own, since it starts from the sheet resting on the button — which is what the hop before it is for. |
| Whether the failed path also hops | No — it turns back from where it rests | Hop on both outcomes, for symmetry | The hop exists to make a layer change invisible, and the failed path already has such a moment: going back the way it came clears the button partway through. Adding one anyway would spend a beat on nothing, and read as the drawing being set down deliberately rather than turning back. |
| The failed save's flash | A burst from the button, expanding to fill the screen while it brightens and fades | A uniform full-screen flash; a flash confined to the button | Expanding from the button attributes the failure to the control that was pressed, which a uniform wash doesn't, and it reaches the whole screen, which a flash confined to the button wouldn't — this is the one moment addressed to an adult who may not be looking closely. |
| How a failed save reads without motion | A red flash over the drawing surface at the rebound's turn, which stands alone as the whole feedback where the platform reports reduced motion | Motion alone, with no flash; a persistent red tint until the next successful save; red on the snapshot's border only | Motion alone leaves nothing to degrade to, and a saved drawing degrades gracefully on its own — the cleared canvas still acknowledges it — so failure is the only case needing a fallback at all. Color also reaches an adult across the room in a way a half-second rebound doesn't, and a failed save is addressed to them. Firing at the turn ties it to the moment the drawing fails to go anywhere. A border-only flash is too fine to carry the signal once the travel is gone, and a persistent tint is ruled out for the same reason as any other standing failure marker. |
| Making the travelling snapshot legible against the canvas | A border on the snapshot for the flight's duration | Nothing — rely on the drawing's own content; a drop shadow; a scale-down that starts immediately so size alone distinguishes it | The canvas behind is a fresh one and the snapshot's own background is the same color, so an unmarked snapshot is near-white over near-white: only the strokes would appear to move, reading as a drawing dissolving rather than a sheet being put away. A border is the cheapest thing that makes it one object. A drop shadow reads as *lifted* and is the vocabulary the New Picture button already uses, so it stays available if the border proves too stark. |
| What a failed save leaves behind once the rebound finishes | Nothing on the kid canvas — the drawing staying put is the only lasting trace | A persistent marker on the canvas until the next successful save | A failed save is addressed to an adult; a toddler can do nothing about a write that didn't land. But a persistent marker is the visible-but-inert affordance the toddler-usability tenet rules out, and it would be poked. The conditions that cause this (storage full, media unmounted) don't resolve on their own, so the rebound recurs on every press and re-announces itself for as long as it's true. A standing adult-facing signal belongs on the companion screen, where a parent already goes to find their child's drawings — see Open Questions. |

## Open Questions & Future Decisions

### Resolved

1. ✅ User Experience observes UX-config changes live, not just at launch — Config exposes a reactive/observable read API. See the Config LLD's Reads Are Reactive section.
2. ✅ Painting is a hoisted-state Compose pattern owning its own pointer input, taking the interaction lock for its own gesture rather than reporting liveness back to User Experience — see the Painting LLD's Composable Shape and Holding the Interaction.
3. ✅ A resolved brush's color can change automatically between strokes, without a new toddler tap — today's stroke color source is `RandomColor`, sampling a fresh color every stroke. See Interaction Feedback and the Painting Style LLD's Color Sources.
4. ✅ A held interaction excludes every other component and every other control, while the holder's own concurrent pointers are the holder's own business to interpret — Painting draws all of them, a control ignores every one but the pointer it claimed. See Input Arbitration's Holding section.
5. ✅ `KidCanvasScreen` composes Widgets (New Picture) alongside Painting and owns the `InteractionLock` both of them take — see Screen Composition, Input Arbitration, and Lifecycle Behavior's New Picture section.
6. ✅ A New Picture auto-save that fails is retried once, and a second failure ends the sequence without clearing, leaving the drawing on the canvas — see Lifecycle Behavior's New Picture section. What the toddler is shown when that happens is #7 below.
7. ✅ New Picture answers the toddler with the drawing's own motion — under the New Picture button when the save landed, a rebound to full size when it didn't — so the two outcomes are distinguishable and neither resembles a press that never registered. See Lifecycle Behavior's Putting the Drawing Away.
8. ✅ Neither the cover nor the arriving sheet needs User Experience to know the canvas's background color. The cover is white because it is the bare surface between two sheets rather than a stand-in for the canvas, and a freshly resolved background arrives on the sheet carrying it — a second snapshot, taken after `clear()`. See Putting the Drawing Away.

### Deferred

1. Per-feature gating granularity: once the feature set grows past the current single bundle, which features become independently toggle-able needs its own pass — including whether/at what age OS back navigation is ever re-enabled. Feature Gating itself has no implementation yet — Config's resolved-feature values aren't read anywhere in `KidCanvasScreen`, so every Widgets control it composes is unconditional.
2. Exact composition geometry — which edge each Widgets control anchors to, spacing, sizing — is deferred to implementation and visual design, not fixed here.
3. How `StyleSettings`' implementation constructs a correctly typed and colored brush instance once Painting Style supports more than one brush type is that LLD's own open question (see its Open Questions #4) — today's single-brush-type implementation just constructs that one type directly with a color from a `ColorSource`.
4. Ownership of the HLD's first-launch adult setup dialog (age slider, device-lock button, link into the Companion App, "don't show again" toggle) isn't assigned to any Kid Canvas component yet. User Experience, as the kid canvas's composition root, is the likely owner, but this LLD doesn't cover it — today's screen composition and lifecycle behavior are defined without it.
5. What resolved-feature values User Experience reads before Config's UX configuration has ever been written (first run, before any dialog or Companion App write) is Config's own default-resolution question, not decided here — see the Config LLD.
6. Color Picker has no implementation yet — `KidCanvasScreen` composes only New Picture today. Color selection's `StyleSettings` wiring (see Interaction Feedback) and OS back-gesture consumption (see OS Navigation and Process Lifecycle) are similarly unimplemented.
7. Whether the drawing surface's orientation should be locked to preclude live device rotation entirely, and if so, whether that lock applies unconditionally or is itself age-gated (see Feature Gating), isn't decided. The motivating concern is visual, not data-survival: rotating the canvas mid-session risks a jarring rotate-then-settle glitch a toddler-usability-first design would rather avoid than merely survive. `android:screenOrientation="locked"` — freezing to whichever orientation is active at launch rather than forcing a fixed portrait or landscape — is the leading candidate if this is pursued, since it defers to the user's own auto-rotate/manual-lock setting instead of overriding it. Rotation is left available for now, since it also exercises the same saved-instance-state survival path other configuration changes and process death use, which is otherwise harder to trigger for testing.
8. Arbitration handles hover only to the extent of staying out of its way: no component reacts to a hovering pointer today, so the guarantees stop at hover never taking the interaction and never being consumed as though it were part of a gesture (see Input Arbitration's When to ask). Giving a control a hover affordance needs three things revisited first. A refused gesture's drain consumes every event until no pointer is pressed, hover events included — even ones belonging to a different pointer with nothing to do with the refused press — so a hover affordance would go dead for the duration of someone else's refused touch, which is wrong. Widgets' hit-testing enters through Compose's `awaitFirstDown`, which returns only when *every* change in an event is a touch-down, so a pointer hovering a control while another touches it keeps that control from ever claiming the touch. And whether an `Exit` is delivered when a hovering pointer presses determines whether a hover affordance clears itself on press or has to be cleared explicitly. None of the three can arise on a touch-only device, so none is worth settling before a control actually wants hover. The hover behavior that *is* implemented — CANVAS-UX-027 and CANVAS-PAINT-024, which keep a hovering pointer from taking the interaction or reaching the drawing — rests on reading the code rather than on tests: the test harness injects touch, and a touch pointer is always pressed, so no test can produce a hovering one.
9. A New Picture sequence cancelled after its `save()` completed but before its `clear()` leaves the drawing on the canvas *and* a copy of it already in Image Storage; pressing New Picture again then writes a second entry for the same drawing. Today this is accepted rather than solved — the cost is one redundant entry in a gallery the parent can already delete from, in a race that needs a screen recreation to land inside the save window. The flight doesn't widen that window: the clear runs before the snapshot starts moving (see Putting the Drawing Away), so the gap between the write and the clear is the same one it always was.

    Retaining the id `save()` returns, and passing it back to update that entry instead of creating another, is the obvious-looking fix and is not sufficient: the id doesn't exist until the write returns, cancellation is delivered at exactly that resumption, and the recreation's state snapshot can be captured before the write completes at all. It narrows the window to the write itself, which is nearly the whole sequence. Closing it properly means deciding a drawing's identity *before* the write — a caller-supplied key that a create-or-update-by-key operation matches on — which Image Storage's current data shape rules out (ids are storage-minted and never caller-invented, and MediaStore assigns its own row id), so it would need a separate key field and a uniqueness rule of its own.

10. A standing, adult-facing indication that saves are failing has no home yet. The rebound recurs on every press for as long as the condition lasts, which is what an adult in the room sees, but nothing tells a parent who wasn't there that their child's drawings stopped arriving. The companion screen — where a parent already goes to browse saved drawings — is where such a signal belongs, and it doesn't exist yet. Putting it on the kid canvas instead is ruled out rather than deferred; see Decisions & Alternatives.
11. Nothing sources the reduced-motion preference yet: the screen honors it, but every caller passes false, so the fallback path is reachable only from a test (CANVAS-UX-039). Android exposes more than one candidate signal — the animator duration scale and the accessibility service's own reduce-motion state — and they don't mean quite the same thing, which is why picking one is its own decision rather than part of building the feedback.
12. Motion beyond what the two movements already use — paper-like easing, a squash at the rebound's turn, a slight tilt on the lift — is still wanted; what's there now is legible rather than finished.
13. Whether the New Picture button itself reacts as the drawing arrives under it — a small acknowledging motion of its own — is Widgets' to decide, since a control's own animation belongs to that control. Nothing in this LLD depends on the answer.
