# Widgets

## Context and Design Philosophy

Widgets implements KidWidgets, the library of on-screen controls (buttons, color picker, and similar chrome) used everywhere on the kid canvas. Standard Compose gesture recognizers (`clickable()`, Material's ripple/gesture stack) assume adult motor control — a precise tap, a drag-cancel-on-outside-release convention, timing tuned for an adult's touch. Toddlers can't reliably produce that input, so every control here reads raw pointer events directly (`Modifier.pointerInput` / `awaitPointerEventScope`) and defines its own hit-testing and activation from scratch, rather than composing standard clickable modifiers.

Widgets doesn't decide *whether* a given touch is even its own to interpret — it just does its own ordinary hit-testing on whatever pointer Compose delivers to it. Keeping that pointer from ever reaching a control while some other gesture is live elsewhere on screen is User Experience's job, done by covering Widgets entirely for that duration rather than by Widgets checking any state of its own (see the User Experience LLD's Input Arbitration section). Widgets' own job is narrower: given a pointer, decide reliably which control (if any) it activates.

## Hit-Testing and Activation

A control's hit region claims whatever pointer lands inside it on `down` — ordinary Compose pointer dispatch, no custom pre-arbitration step (see Interaction Arbitration Contract). That claim is fixed for the rest of the pointer's gesture: dragging an already-down pointer into a control's region never claims it, and once a pointer is claimed, dragging it into a *different* control's region doesn't reassign it there either. Press feedback appears the instant a pointer is claimed, well before the activation decision below is made, so a toddler gets some visible response to every touch immediately, whether or not it ultimately activates anything.

Whether a claimed pointer ends in activation is decided at its release, not at `down` — but not with `clickable()`'s zero-tolerance rule either, since a toddler's finger commonly drifts just outside a control's region in the final moment of lifting off, observed directly in testing with an actual toddler tester. Each control tracks two timestamps as its claimed pointer moves: when it most recently entered the hit region (or the initial down time, if it never left), and when it most recently exited (unset while inside). At release: if the pointer is currently inside the region, the control activates. If it's currently outside, the control still activates when the time spent outside is under roughly 100ms *and* less than the time spent inside immediately before that — a brief lift-off wobble a toddler didn't intend as an exit. Otherwise the gesture ends with no activation, exactly as if the pointer had been dragged well away and released there. A drift toward a neighboring control's region (most likely between adjacent Color Picker swatches) is measured against the *originally claimed* control's own bounds, not the one the pointer drifted into — consistent with control assignment being fixed at `down`.

Hit regions are sized generously beyond each control's visible glyph, tolerant of imprecise placement — the visible control and its tappable area are not the same rectangle. Exact sizing, and the exact stray/inside thresholds above, are tuning decisions expected to be refined from real testing data rather than fixed here (see Open Questions).

## Reporting Press State

Each control instance takes two callbacks. `onPressedChange: (Boolean) -> Unit` is invoked with `true` the moment a pointer is claimed and `false` when that same pointer lifts — an unconditional lifecycle signal that always fires both edges, regardless of whether the press ends up activating anything. `onActivate: () -> Unit` is invoked once, at that same lift, but only when the release counts as an activation (see Hit-Testing and Activation). These used to be the same event, back when activation happened at `down`; now that activation depends on how a gesture *ends*, the two have to be reported separately — User Experience's blocking-layer arbitration (see the User Experience LLD's Input Arbitration) needs to know a gesture is live the instant a pointer is claimed, which `onPressedChange` still provides unconditionally, while the control's actual action can only be decided once the release itself is evaluated. A composable has no persistent object identity to expose a `Flow` from, so callbacks — the same shape Compose's own stateful controls (e.g. `Switch`'s `onCheckedChange`) use — are the idiomatic way to surface both, rather than the control returning or holding onto a reactive stream itself.

A control with multiple independent hit regions (Color Picker) takes one pair of callbacks per region instance, since each swatch is its own independent activation target — the caller composing a given swatch already knows which color it represents, so nothing needs to flow back through either callback beyond the boolean and the activation event themselves.

## Control Catalog

Two controls exist today:

- **Button** — a single hit region, one activation action (e.g. New Picture).
- **Color Picker** — multiple hit regions, one per color swatch, each an independent activation target following the same hit-testing and activation rule as Button; activating a swatch selects that color.

Both are built on the same underlying raw-pointer hit-testing and activation primitive described above — Widgets doesn't have a separate mechanism per control type. A new control follows the same primitive without needing its own hit-testing logic.

## Interaction Arbitration Contract

Widgets doesn't arbitrate against Painting itself, and doesn't know Painting or strokes exist. Whether a given pointer even reaches a control at all is decided upstream, before Widgets' own hit-testing ever runs: User Experience composes a transparent, pointer-consuming layer over Widgets for the duration of any gesture Painting is holding (see the User Experience LLD's Input Arbitration section), so a pointer that would otherwise land inside a control's hit region never reaches it while a stroke is live. Because of that upstream blocking, Widgets never observes a second, concurrent pointer while it's tracking one — the re-trigger and cross-control drag rule above only has to reason about a single pointer's own events over time, never about competing simultaneous pointers. Widgets depends on nothing beyond the pointer events Compose's own hit-testing delivers to it and the `onPressedChange`/`onActivate` callbacks it's given.

## System Gesture Coexistence

A control's hit region can end up wherever User Experience anchors it (see the User Experience LLD's Screen Composition), including flush against a screen edge — and on Android, the OS reserves the edges for its own gesture navigation (the back-swipe strip along the left and right edges). A toddler's touch that starts inside a control's hit region but lands within that reserved strip risks being intercepted by the OS as a system gesture rather than reaching the control at all — the same "hands accidentally leave the app" failure the toddler-usability tenet already rules out, this time via the OS rather than an in-app control.

Widgets closes that gap the same way it already reasons about hit-testing: using each control's own on-screen bounds, already computed for Hit-Testing and Activation, to register that region with the platform as excluded from system gesture handling. On Android this is `View.setSystemGestureExclusionRects`; platforms without an equivalent concept simply have nothing to register. This applies unconditionally to every control, not only ones User Experience happens to place near an edge — a control away from any gesture zone registers an exclusion rect that has nothing to exclude, at no real cost, and Widgets stays as ignorant of *why* it might be near an edge as it already is of Painting or User Experience's own placement choices.

The platform API takes one combined list for the whole app window rather than per-control registration, so Widgets aggregates every currently-mounted control's rect into that one list itself — each control registering or unregistering its own rect only ever changes its own entry, never displacing another control's. A control's registered rect also stays in sync with its actual on-screen bounds for as long as it's mounted, not just at its initial composition, since registration rides the same layout callback that fires again on any later bounds change.

This doesn't cover the bottom edge's home/overview gesture — the OS reserves that gesture from app-level exclusion entirely, so no control placed near the bottom edge can rely on this mechanism to avoid triggering it. Keeping such a control's hit region off the bottom edge in the first place is the only way to avoid that failure mode (see the User Experience LLD's Screen Composition for where controls are actually placed).

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Activation trigger | Release (pointer-up) while still inside the hit region — or, if the pointer drifted outside just before lifting, only when that drift was brief (under roughly 100ms) and shorter than how long the pointer had been validly inside beforehand; press feedback still appears immediately at `down` | (1) Pointer-down inside the hit region, firing instantly with no release step at all (the original design); (2) standard `clickable()` release semantics — any exit from the hit region cancels the press outright, with no tolerance for drift | Down-only firing (1) has no defense against an incidental touch that merely grazes the region — anything landing inside fires it, whether the toddler meant to or not. Zero-tolerance release (2) rejects a large fraction of genuine presses, since a toddler's finger commonly drifts just outside the region in the final moment of lifting off, observed directly in testing. The chosen tolerance keeps both: an incidental graze that never really settles inside doesn't fire, and a real press whose lift-off merely wobbles outside still does. |
| Whether activation and press-lifecycle are one signal or two | Two callbacks: `onPressedChange` (unconditional down/up lifecycle, used for User Experience's blocking-layer arbitration) and `onActivate` (fires only on a release that counts as an activation) | One `onPressedChange` callback whose `true` edge both marks gesture-start and fires the action — viable under the original down-triggers-everything design, where the two coincided | Once activation depends on how a gesture ends rather than how it begins, gesture lifecycle (needed immediately, for arbitration) and activation (only knowable at release, conditionally) can no longer be the same event. Splitting them keeps arbitration timing exactly as before — a gesture is still "live" the instant a pointer is claimed — while activation firing moves to wherever the stray-tolerance check resolves it. |
| Re-trigger and cross-control drag handling | A pointer's control assignment (if any) is fixed at its own down event; dragging into a different control's region never reassigns it there, and a released pointer can activate its assigned control at most once | Re-evaluate hit-testing continuously as the pointer moves, activating whichever control it's currently over | A single decide-once-at-down assignment rule is simple to reason about and prevents a dragging or resting hand from "sliding" an activation from one control to another; each pointer can only ever produce the one release its own gesture ends with, so repeated firing from a single pointer isn't otherwise possible either. |
| How Widgets learns it's blocked while another gesture is live | It isn't told anything — User Experience composes a pointer-consuming transparent layer over all of Widgets for the blocked duration, so a blocked pointer never reaches any control's own hit-testing at all | An explicit boolean `enabled` gate Widgets checks per pointer; Widgets observing Painting's stroke state directly | A covering layer needs no signal from Painting or User Experience to reach Widgets at all — every pointer Widgets' own hit-testing ever sees is unambiguously its own, exactly like a plain, unarbitrated Compose screen would see. |
| Hold/long-press activation | Not supported by any control today — every control is a single tap-and-release | Support a hold/long-press variant for some controls | The HLD explicitly rejects a long-press requirement for toddler-facing controls, and no current control needs one. Not a permanent constraint on the library itself — a future control could still add one if a genuine need arises. |
| Preventing a control's hit region from being intercepted by the OS's own edge-swipe gesture recognition | Every control unconditionally registers its own current on-screen bounds as a system gesture exclusion rect (`View.setSystemGestureExclusionRects` on Android; a no-op where the platform has no equivalent) | Have User Experience tell Widgets which controls are edge-anchored and only exclude those; rely on inset-only placement (keeping controls a few dp off the true edge) with no exclusion at all; rely on Android's "insistent swipe" override, which lets a wide-enough swipe through even inside an excluded region, as the sole safeguard | Widgets already computes each control's own bounds for hit-testing, so reusing them for exclusion needs no new state and no signal from User Experience about *why* a control might be near an edge — consistent with Widgets' existing ignorance of Painting and User Experience's placement decisions. Applying it to every control costs nothing where there's no gesture zone to exclude. Inset-only placement and the insistent-swipe override are real mitigations but leave a toddler's ordinary, non-insistent touch near the true edge unprotected — the actual failure mode observed, not just permanent lockout. |
| Callback vs. reactive stream for both signals | Plain callbacks (`onPressedChange`, `onActivate`) | A `Flow<Boolean>`/`Flow<Unit>` the control exposes, collected by the caller | A composable is a function re-invoked on recomposition, with no persistent object identity to hang a `Flow` off of without extra caller-side machinery, so callbacks are the idiomatic shape — matching Compose's own stateful controls (e.g. `Switch`'s `onCheckedChange`). |

## Open Questions & Future Decisions

### Resolved

1. ✅ A control's registered gesture-exclusion rect stays in sync with its on-screen bounds for as long as it's mounted, not just at initial composition — registration rides the same layout callback that fires again on any later bounds change (e.g. a device rotation that shifts the control). See System Gesture Coexistence.

### Deferred

1. Exact hit-region sizing/tolerance beyond the visible glyph is a visual-design decision, not fixed here.
2. Full control catalog beyond Button and Color Picker isn't enumerated ahead of need — new controls follow the existing primitive.
3. The stray-tolerance threshold (roughly 100ms) and the "stray shorter than the preceding time spent inside" rule are a first guess, not yet tuned against real usage data — expected to be refined once real-world testing data is available.
