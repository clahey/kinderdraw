# Widgets

## Context and Design Philosophy

Widgets implements KidWidgets, the library of on-screen controls (buttons, color picker, and similar chrome) used everywhere on the kid canvas. Standard Compose gesture recognizers (`clickable()`, Material's ripple/gesture stack) assume adult motor control — a precise tap, a drag-cancel-on-outside-release convention, timing tuned for an adult's touch. Toddlers can't reliably produce that input, so every control here reads raw pointer events directly (`Modifier.pointerInput` / `awaitPointerEventScope`) and defines its own hit-testing and activation from scratch, rather than composing standard clickable modifiers.

Widgets does its own ordinary hit-testing on whatever pointer Compose delivers to it, and then asks the screen's interaction lock whether that pointer is its to interpret at all (see Interaction Arbitration Contract). It never learns what else might be using the screen, only whether it may act. Widgets' own job is narrower than arbitration: given a pointer it's allowed to claim, decide reliably which control (if any) it activates.

## Hit-Testing and Activation

A control's hit region claims whatever pointer lands inside it on `down`, provided the interaction lock grants it the interaction at that same moment (see Interaction Arbitration Contract) — ordinary Compose pointer dispatch plus that one question, not a custom routing step of Widgets' own. That claim is fixed for the rest of the pointer's gesture: dragging an already-down pointer into a control's region never claims it, and once a pointer is claimed, dragging it into a *different* control's region doesn't reassign it there either. Press feedback appears the instant a pointer is claimed, well before the activation decision below is made, so a toddler gets some visible response to every touch the control was allowed to claim, whether or not it ultimately activates anything. A pointer the lock refuses is never claimed at all, and so produces no feedback — a control that may not act must not look like it did.

Whether a claimed pointer ends in activation is decided at its release, not at `down` — but not with `clickable()`'s zero-tolerance rule either, since a toddler's finger commonly drifts just outside a control's region in the final moment of lifting off, observed directly in testing with an actual toddler tester. Each control tracks two timestamps as its claimed pointer moves: when it most recently entered the hit region (or the initial down time, if it never left), and when it most recently exited (unset while inside). At release: if the pointer is currently inside the region, the control activates. If it's currently outside, the control still activates when the time spent outside is under roughly 100ms *and* less than the time spent inside immediately before that — a brief lift-off wobble a toddler didn't intend as an exit. Otherwise the gesture ends with no activation, exactly as if the pointer had been dragged well away and released there. A drift toward a neighboring control's region (most likely between adjacent Color Picker swatches) is measured against the *originally claimed* control's own bounds, not the one the pointer drifted into — consistent with control assignment being fixed at `down`.

A claimed press ends one of three ways, and only two of them can activate: the pointer lifts inside the region, the pointer lifts outside it (activating only under the stray tolerance above), or the press is **cancelled** — the control leaves the screen, or its pointer input is reset out from under it, while the pointer is still down. A cancelled press never activates, however long the pointer had been sitting inside the hit region. Nothing about the toddler's touch decided it, so treating it as a press that succeeded would fire an action nobody asked for; New Picture, the one destructive action on the screen, is exactly the control where that matters. Cancellation still ends the press for every other purpose — press feedback clears, and the control's hold on the interaction is released (see Interaction Arbitration Contract) — so a cancelled press is a press that ended, not one left hanging.

Distinguishing a cancellation from a release is the control's own job, before it consults the activation rule. The rule itself is asked only about genuine releases, and answers only the timing question.

Nothing in today's screen can actually cancel a press. Device rotation is the scenario that suggests itself, and Android rules it out: the OS defers rotation while a touch is down, so the recreation never lands mid-gesture — confirmed on a device, not inferred. That leaves the rules below describing behavior no current path reaches. They are still worth stating, because the paths that do reach them are ordinary rather than exotic: a control removed while the screen stays (feature gating is the nearest example — see the User Experience LLD's Feature Gating), a pointer input reset under a live control, or any control whose presence comes and goes.

The two ways a press can be cancelled look identical to the activation decision and differ in what survives them. A control removed from the screen takes its own rendering with it, so its press feedback has nothing left to clear, and whatever else was scoped to it — including an activation already under way — is cancelled alongside. A pointer input reset under a control that stays on screen leaves both the control and its surroundings alive, so feedback that isn't cleared stays visible and a running activation keeps running. The rules above hold in both cases; only their observable consequences differ.

Hit regions are sized generously beyond each control's visible glyph, tolerant of imprecise placement — the visible control and its tappable area are not the same rectangle. Exact sizing, and the exact stray/inside thresholds above, are tuning decisions expected to be refined from real testing data rather than fixed here (see Open Questions).

## Reporting Activation

Each control instance takes one callback outward: `onActivate: suspend () -> Unit`, invoked once when a claimed pointer's release counts as an activation (see Hit-Testing and Activation), and not at all when it doesn't. A composable has no persistent object identity to expose a `Flow` from, so a callback — the same shape Compose's own stateful controls (e.g. `Switch`'s `onCheckedChange`) use — is the idiomatic way to surface it, rather than the control returning or holding onto a reactive stream.

It suspends because a control keeps the interaction until its activation's own work has finished (see Interaction Arbitration Contract): an action that waits on storage keeps the screen to itself for that whole span, while an instantaneous one returns at once and behaves exactly like a plain callback. The control runs it in a scope tied to its own composition rather than to the pointer-event stream, so the release that triggered an action never cancels the action it triggered.

A control's press state isn't reported outward at all — the control hands it to its own rendering, which is the only thing that ever needed it. Nothing outside the control has to know a press is underway now that the control takes the interaction itself. Press feedback clears at whichever of the three endings arrives, cancellation included, so no control can be left rendering a press that is over.

A control with multiple independent hit regions (Color Picker) takes one `onActivate` per region instance, since each swatch is its own independent activation target — the caller composing a given swatch already knows which color it represents, so nothing needs to flow back through the callback beyond the activation event itself.

## Control Catalog

Two controls exist today:

- **Button** — a single hit region, one activation action (e.g. New Picture).
- **Color Picker** — multiple hit regions, one per color swatch, each an independent activation target following the same hit-testing and activation rule as Button; activating a swatch selects that color.

Both are built on the same underlying raw-pointer hit-testing and activation primitive described above — Widgets doesn't have a separate mechanism per control type. A new control follows the same primitive without needing its own hit-testing logic.

## Interaction Arbitration Contract

Widgets doesn't arbitrate against Painting itself, and doesn't know Painting or strokes exist. Each control takes an `InteractionLock` — defined and owned by User Experience, which creates one per screen (see its Input Arbitration section) — asks it for the interaction the moment a pointer lands inside the control's hit region, before claiming that pointer:

- **Granted.** The control claims the pointer and holds the interaction until its own gesture is over: released at a release that activates nothing, and at the end of the activation's own work for one that does, the control having handed its hold to that work rather than releasing at the press. That release is unconditional on how things ended — returning normally, failing, or being cancelled all release it — so a failed action leaves the screen usable rather than locked, and no hold outlives the control that took it.
- **Refused.** The control never claims the pointer and shows no press feedback; the gesture is consumed to its last pointer's lift. Its own press-handling doesn't run at all, so there's nothing for it to undo and nothing for it to release.

Holding through activation is what lets an asynchronous action keep the screen to itself for its whole duration without its caller arranging anything (New Picture's save-then-clear is the case that needs it — see the User Experience LLD's Lifecycle Behavior).

A second pointer arriving while a control is tracking one is not a second claim, whichever control it lands on: another control's request is refused by the lock, and a pointer landing on the holding control itself is simply ignored, since a control tracks only the pointer it claimed for the rest of that gesture. So the re-trigger and cross-control drag rules above only ever reason about a single pointer's own events over time, never about competing simultaneous pointers.

Widgets depends on nothing beyond the pointer events Compose's own hit-testing delivers to it, the lock it's given, and the `onActivate` callback.

## System Gesture Coexistence

A control's hit region can end up wherever User Experience anchors it (see the User Experience LLD's Screen Composition), including flush against a screen edge — and on Android, the OS reserves the edges for its own gesture navigation (the back-swipe strip along the left and right edges). A toddler's touch that starts inside a control's hit region but lands within that reserved strip risks being intercepted by the OS as a system gesture rather than reaching the control at all — the same "hands accidentally leave the app" failure the toddler-usability tenet already rules out, this time via the OS rather than an in-app control.

Widgets closes that gap the same way it already reasons about hit-testing: using each control's own on-screen bounds, already computed for Hit-Testing and Activation, to register that region with the platform as excluded from system gesture handling. On Android this is `View.setSystemGestureExclusionRects`; platforms without an equivalent concept simply have nothing to register. This applies unconditionally to every control, not only ones User Experience happens to place near an edge — a control away from any gesture zone registers an exclusion rect that has nothing to exclude, at no real cost, and Widgets stays as ignorant of *why* it might be near an edge as it already is of Painting or User Experience's own placement choices.

The platform API takes one combined list for the whole app window rather than per-control registration, so Widgets aggregates every currently-mounted control's rect into that one list itself — each control registering or unregistering its own rect only ever changes its own entry, never displacing another control's. A control's registered rect also stays in sync with its actual on-screen bounds for as long as it's mounted, not just at its initial composition, since registration rides the same layout callback that fires again on any later bounds change.

This doesn't cover the bottom edge's home/overview gesture — the OS reserves that gesture from app-level exclusion entirely, so no control placed near the bottom edge can rely on this mechanism to avoid triggering it. Keeping such a control's hit region off the bottom edge in the first place is the only way to avoid that failure mode (see the User Experience LLD's Screen Composition for where controls are actually placed).

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Activation trigger | Release (pointer-up) while still inside the hit region — or, if the pointer drifted outside just before lifting, only when that drift was brief (under roughly 100ms) and shorter than how long the pointer had been validly inside beforehand; press feedback still appears immediately at `down` | (1) Pointer-down inside the hit region, firing instantly with no release step at all (the original design); (2) standard `clickable()` release semantics — any exit from the hit region cancels the press outright, with no tolerance for drift | Down-only firing (1) has no defense against an incidental touch that merely grazes the region — anything landing inside fires it, whether the toddler meant to or not. Zero-tolerance release (2) rejects a large fraction of genuine presses, since a toddler's finger commonly drifts just outside the region in the final moment of lifting off, observed directly in testing. The chosen tolerance keeps both: an incidental graze that never really settles inside doesn't fire, and a real press whose lift-off merely wobbles outside still does. |
| What a control reports outward | `onActivate` only, fired on a release that counts as an activation; press state goes to the control's own rendering rather than to the caller | An additional unconditional `onPressedChange` down/up pair the caller can arbitrate with; one callback whose down edge both marks the gesture live and fires the action | Press lifecycle was only ever reported outward so something above could arbitrate with it; a control that takes the interaction itself leaves no caller needing it, and a callback nothing consumes is a contract to maintain for free. Activation stays its own event because it can only be decided at release, once the stray-tolerance check resolves. |
| Whether `onActivate` suspends | `suspend () -> Unit`, run in a composition-scoped coroutine, with the control's hold on the interaction lasting until it returns | A plain `() -> Unit` that returns immediately, with the caller launching its own asynchronous work and separately telling the control when to release | An action whose work outlives the press is exactly when arbitration matters most — the window where a touch would otherwise be accepted and then invisibly undone. Making the action's completion the thing the hold waits on puts the control's release on the same timeline as the work, instead of on a second signal a caller has to remember to send. Instant actions are unaffected: they return at once and behave as a plain callback would. |
| How a cancelled press is expressed | A distinct ending the control reports explicitly, separate from a release: the activation rule is consulted only for genuine releases, and never sees a cancellation | Report a cancellation as an ordinary release and let the activation rule reject it; report nothing at all and let the control unwind its own press state | The activation rule judges timing — how long the pointer sat inside the region before lifting — and by that measure a cancelled press is indistinguishable from a deliberate one, so routing a cancellation through it activates the control. Reporting nothing leaves the press with no ending at all: feedback stays lit and the control has to unwind by hand, which is the state a press-lifecycle abstraction exists to prevent. Making cancellation its own ending means every way a press can end has exactly one place to go. |
| Re-trigger and cross-control drag handling | A pointer's control assignment (if any) is fixed at its own down event; dragging into a different control's region never reassigns it there, and a released pointer can activate its assigned control at most once | Re-evaluate hit-testing continuously as the pointer moves, activating whichever control it's currently over | A single decide-once-at-down assignment rule is simple to reason about and prevents a dragging or resting hand from "sliding" an activation from one control to another; each pointer can only ever produce the one release its own gesture ends with, so repeated firing from a single pointer isn't otherwise possible either. |
| How Widgets learns it may not act while another gesture is live | It asks the interaction lock at the instant a pointer lands inside a hit region, and refuses that whole gesture if the lock refuses | User Experience composing a pointer-consuming transparent layer over all of Widgets for the blocked duration, so a blocked pointer never reaches a control at all; an explicit boolean `enabled` gate Widgets checks per pointer; Widgets observing Painting's stroke state directly | Asking at the moment of the decision means a control's view of whether it may act can't be stale, which both a covering layer (correct only if whoever raises it has current liveness for both children) and an `enabled` flag (a snapshot from some earlier moment) depend on being. It also costs Widgets no knowledge of Painting: the lock answers *whether*, never *who*, where observing stroke state directly would make Widgets aware Painting exists. |
| Hold/long-press activation | Not supported by any control today — every control is a single tap-and-release | Support a hold/long-press variant for some controls | The HLD explicitly rejects a long-press requirement for toddler-facing controls, and no current control needs one. Not a permanent constraint on the library itself — a future control could still add one if a genuine need arises. |
| Preventing a control's hit region from being intercepted by the OS's own edge-swipe gesture recognition | Every control unconditionally registers its own current on-screen bounds as a system gesture exclusion rect (`View.setSystemGestureExclusionRects` on Android; a no-op where the platform has no equivalent) | Have User Experience tell Widgets which controls are edge-anchored and only exclude those; rely on inset-only placement (keeping controls a few dp off the true edge) with no exclusion at all; rely on Android's "insistent swipe" override, which lets a wide-enough swipe through even inside an excluded region, as the sole safeguard | Widgets already computes each control's own bounds for hit-testing, so reusing them for exclusion needs no new state and no signal from User Experience about *why* a control might be near an edge — consistent with Widgets' existing ignorance of Painting and User Experience's placement decisions. Applying it to every control costs nothing where there's no gesture zone to exclude. Inset-only placement and the insistent-swipe override are real mitigations but leave a toddler's ordinary, non-insistent touch near the true edge unprotected — the actual failure mode observed, not just permanent lockout. |
| Callback vs. reactive stream for activation | A plain callback (`onActivate`) | A `Flow<Unit>` the control exposes, collected by the caller | A composable is a function re-invoked on recomposition, with no persistent object identity to hang a `Flow` off of without extra caller-side machinery, so a callback is the idiomatic shape — matching Compose's own stateful controls (e.g. `Switch`'s `onCheckedChange`). |

## Open Questions & Future Decisions

### Resolved

1. ✅ A control's registered gesture-exclusion rect stays in sync with its on-screen bounds for as long as it's mounted, not just at initial composition — registration rides the same layout callback that fires again on any later bounds change (e.g. a device rotation that shifts the control). See System Gesture Coexistence.

### Deferred

1. Exact hit-region sizing/tolerance beyond the visible glyph is a visual-design decision, not fixed here.
2. Full control catalog beyond Button and Color Picker isn't enumerated ahead of need — new controls follow the existing primitive.
3. The stray-tolerance threshold (roughly 100ms) and the "stray shorter than the preceding time spent inside" rule are a first guess, not yet tuned against real usage data — expected to be refined once real-world testing data is available.
4. `InteractionLock` is a concrete class owned by User Experience, so KidWidgets currently can't be lifted out of this app without it. If the library is ever extracted for reuse, the shape that fixes this is for Widgets to own a minimal interface for what it actually needs — may I claim, I'm done — and for `InteractionLock` to implement it. Not worth doing before there's a second consumer.
