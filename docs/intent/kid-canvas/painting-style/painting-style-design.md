# Painting Style

## Context and Design Philosophy

Painting Style defines what a stroke or the canvas background actually looks like — brush shape and color — independent of how a touch sequence becomes captured stroke data (Painting) or how the screen is orchestrated (User Experience). It's a library of pluggable rendering and color strategies with no state of its own beyond what each strategy instance is constructed with, and no dependency on either component that consumes it: Painting depends on Painting Style for its brush/stroke rendering strategy and its `Point` coordinate type, and User Experience depends on it for the color sources behind `StyleSettings`, but Painting Style depends on neither.

## Point

A point is stored relative to the drawing surface's center, in units of the shorter of the canvas's width and height at the moment it was captured — not raw pixels, and not independently-scaled fractions of width and height. Both axes are scaled by the same factor, so a stroke's shape (the relative position of its points to each other) is preserved exactly across any resize, including one that changes the drawing surface's aspect ratio (most commonly a device rotation): scaling both axes uniformly can never stretch a circle into an oval the way scaling them independently would. A device rotation doesn't get any special exemption from what follows below — it's just one more aspect-ratio-changing resize, since portrait's long axis becomes landscape's short axis.

Centering the origin means a resize that changes the drawing surface's aspect ratio — most commonly a device rotation, but any resize where width and height don't scale together — can push points that were far from center outside the new visible bounds: a point captured out near the top or bottom edge of a tall portrait screen, for instance, can end up beyond the shorter, now-vertical edge once the screen rotates to landscape, even though its distance from center in pixels hasn't changed. Nothing is lost from the data — Painting's own stroke storage doesn't clip anything — but a `Canvas` naturally only draws what falls inside its own bounds, so that content simply isn't visible until another resize brings it back into view. This is deliberate: uniformly scaling to always fill the new bounds is exactly the distortion this design avoids, and letterboxing to guarantee nothing is ever off-screen was rejected as wasting drawing area (see the Kid Canvas sub-HLD's screen-layering decision).

`Point(x, y)` is a plain value type — signed, since a point left of or above center is negative — with two conversions: `Offset.toPoint(size): Point` (capture-time, used by Painting's own pointer-input handling to turn a raw touch position into a `Point`) and `Point.toOffset(size): Offset` (render-time, used by a brush's own rendering — see Brushes). Both live here even though Painting is the one that captures raw pointer input, since this coordinate system exists specifically to serve correct resize-adaptive rendering, a Painting Style concern; Painting depends on Painting Style for `Point` the same way it depends on it for `Brush`/`Stroke`.

## Brushes

A brush owns a stroke's entire lifecycle, not just its final rendering: it creates each stroke that begins under it, and that stroke — not whatever holds the brush — captures the points as they arrive and turns them into rendered pixels (line width, shape, interpolation between points, and any other visual effect). A brush must be able to render a stroke incrementally, extending the visible output as each new point arrives, since a brush's caller (Painting) always renders progressively.

`Brush` is a plain Kotlin interface (`fun startStroke(point: Point): Stroke`, `fun restore(saved: Map<String, Any?>): Stroke`) — a pluggable rendering strategy enforced as a real contract from the start, independent of how many implementations currently satisfy it. `Stroke` is the per-instance interface a brush's `startStroke` returns: `fun addPoint(point: Point)`, `fun DrawScope.render()`, `fun restart(): Stroke` (producing a stroke that continues from this one's current end point with the same settings, for Painting's mid-stroke `clear()` behavior), and `fun save(): Map<String, Any?>` (see Save and Restore below). Neither interface says anything about color or how it's determined — that's each concrete brush's own concern.

### Save and Restore

A stroke's `save()` and its brush's `restore()` are how a stroke survives Painting's own lifecycle-survival mechanism (see the Painting LLD's Lifecycle Survival) without Painting ever needing to know what a stroke is made of. `save()` returns a plain `Map<String, Any?>` — self-describing, not a dedicated named type — because the ultimate destination (Compose's saveable-state storage) is itself dynamically typed with no compile-time schema, so a named wrapper type wouldn't add real type safety, only a level of indirection. Painting's own persistence code (see its Style Settings section) treats this map as opaque: it collects one per stroke and hands each one back to `restore()` unchanged, never inspecting or depending on its contents.

`AbstractSimpleBrush`'s `save()` returns `{"color": <packed color>, "points": <flattened point list>}`; its `restore()` reads that same shape back. A different brush family is free to use an entirely different map shape — nothing about `Brush`/`Stroke`'s contract constrains it — since `save()`/`restore()` are a pair only that brush ever has to keep consistent with itself. Restoration always asks whatever brush is currently active to `restore()` every saved stroke, regardless of which brush actually produced it originally (see Open Questions); with exactly one brush type today, this is exact by construction.

`AbstractSimpleBrush` is the base `Brush` for the common case: a stroke that's just a flat, ordered point list, rendered by a single function seeded with every point captured so far and the stroke's own resolved color. It holds a `ColorSource`, not a resolved color, and is itself long-lived — the same instance answers for every stroke, rather than a fresh one being constructed per stroke. Color is resolved once per stroke, at that stroke's own creation (`startStroke()`), not at the brush's own construction: `AbstractSimpleBrush` queries its `ColorSource` exactly once when a stroke begins, and the resulting `Stroke` — not the brush — holds that color fixed for its own entire rendering lifetime, including across a `restart()` (see Decisions & Alternatives). This is what lets one brush instance answer for many differently colored strokes, matching a `ColorSource` like `RandomColor` that's meant to vary between strokes. `DefaultBrush` is today's only concrete brush: a fixed-width solid line connecting points as a simple polyline, with no curve-fitting or smoothing, holding whatever `ColorSource` it was constructed with.

`AbstractSimpleBrush`'s stroke implementation stores its points via `mutableStateListOf<Point>` rather than a plain list — this is what satisfies Painting's own requirement that a stroke's captured points participate in Compose's draw-phase snapshot observation, so `Painting` redraws as new points arrive with no invalidation signal of its own (see the Painting LLD's Composable Shape).

## Color Sources

`ColorSource` is a plain Kotlin interface — `fun getNextColor(): Color` — pulled from, not pushed to: a caller (a `StyleSettings` implementation, for example) queries it whenever it needs a color, at whatever cadence that caller already operates on (see Style Settings below for Painting's own cadence). `ColorSource` itself has no opinion about cadence.

Two implementations exist:

- **`ConstantColor(color)`** — always returns the same color.
- **`RandomColor(hue, saturation, value)`** — composes a color from three independent `Distribution` "dials," one per HSV channel, each sampled fresh on every `getNextColor()` call. `RandomColor` holds no `Random` of its own — each `Distribution` it's given already owns one. Saturation and value are expected to be fractions in `[0, 1]`; hue is a `[0, 1]` fraction of the full color wheel, scaled to degrees when constructing the resulting color. `RandomColor` clamps its sampled saturation and value into `[0, 1]` before composing the color, rather than trusting a caller's `Distribution` to already be configured within range.

Composing HSV from three independently-distributed channels, rather than one joint distribution over color space, is what lets each channel vary on its own shape — a uniform hue with a non-uniform value channel, for instance — without a combinatorial explosion of joint-distribution classes for every combination anyone might want.

## Distributions

`Distribution` is a plain Kotlin interface — `fun sample(): Float` — used by `RandomColor`'s three channels today, but not tied to color; anything needing a randomized (or fixed) numeric value can depend on it. Each concrete `Distribution` owns its own `kotlin.random.Random` instance, injected at construction and defaulting to `Random.Default`, rather than `sample()` taking one as a parameter — this keeps every `Distribution` self-contained, and lets a test substitute a scripted fake `Random` per instance without threading one through every caller.

Four implementations exist:

- **`ConstantDistribution(value)`** — always returns `value`; no randomness, no `Random` dependency.
- **`UniformDistribution(min, max, random)`** — every value in `[min, max]` is equally likely.
- **`LinearDistribution(min, max, weightAtMin, weightAtMax, random)`** — density increases or decreases linearly across `[min, max]`, with relative density `weightAtMin` at one end and `weightAtMax` at the other. Sampled as a mixture of two branches rather than by inverting the distribution's CDF directly: with probability `weightAtMax / (weightAtMin + weightAtMax)`, sample the increasing branch `sqrt(random.nextFloat())`; otherwise sample the decreasing branch `1 - sqrt(random.nextFloat())` — both are themselves linear (the max, respectively min, of two independent uniform samples, produced via inverse-CDF without solving anything but a square root), and a probability-weighted mixture of two linear densities is itself linear, landing exactly on the requested endpoint weights. Both branches are then scaled from `[0, 1]` into `[min, max]`. `weightAtMin` and `weightAtMax` are read only as a ratio — any two values in the same proportion produce an identical distribution — so they default to `(0, 1)`: a pure increasing ramp, and the least surprising default for a "weight" (a bare `1`, not a value that only makes sense once you know the underlying density function peaks at `2`).
- **`PowerDistribution(min, max, exponent, random)`** — samples `random.nextFloat().pow(1f / exponent)`, scaled from `[0, 1]` into `[min, max]`. `exponent = 1` is uniform; `exponent > 1` biases toward `max` with a density curve that steepens as `exponent` grows (density is proportional to `y^(exponent - 1)`); `exponent < 1` biases toward `min` the same way. `exponent = 2` reproduces `LinearDistribution`'s own pure-increasing-ramp case exactly (`sqrt` is `pow(1/2)`), but `PowerDistribution` isn't limited to a straight-line density the way `LinearDistribution` is, and only biases toward one end at a time — it doesn't have `LinearDistribution`'s two independent endpoint weights.

`weightAtMin` and `weightAtMax` must each be non-negative, and not both zero (a negative or all-zero pair has no valid mixture probability). `UniformDistribution`, `LinearDistribution`, and `PowerDistribution` all also require `min` to be no greater than `max` — a reversed range is rejected rather than silently producing an inverted or negative-width distribution. `PowerDistribution`'s `exponent` must be strictly positive — zero or negative makes `1f / exponent` undefined or sign-reversing in a way that doesn't correspond to any real distribution.

## Style Settings

`StyleSettings` is the interface a consumer queries for the brush and background currently in effect — `fun getActiveBrush(): Brush` and `fun getActiveBackground(): ColorSource` — mirroring the separation the Config LLD's Resolved Features draws between raw state and the value a consumer actually needs.

Both accessors return a long-lived object rather than a single resolved value, though what a caller does with each differs: `getActiveBrush()` returns the same `Brush` instance across calls (see Brushes — the brush itself resolves and fixes a color once per stroke, at that stroke's own creation), while `getActiveBackground()` returns a `ColorSource` a caller queries and caches itself, since a background isn't stroke-scoped the way a brush is.

Painting Style defines `StyleSettings` and its return types, but — unlike `ColorSource` and `Distribution`, whose implementations live here too — doesn't implement it: deciding what "current" means (a toddler's swatch tap, a config value, or, as today, sampling a `ColorSource`) is inherently about screen orchestration, not styling, so the implementation is owned entirely outside Painting Style (today, by User Experience — see its LLD's Interaction Feedback).

Painting is `StyleSettings`' only consumer today. How and when it queries the interface — once per stroke to start a stroke on the active brush, at construction and each `clear()` to resolve and cache a `Color` from the active background `ColorSource` — is Painting's own contract, not part of this interface's definition (see the Painting LLD's Style Settings section).

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Brush as a first-class, pluggable concept | `Brush`/`Stroke` interfaces, enforced as a real contract from the start | Hardcode the single line-rendering algorithm directly wherever strokes are rendered, with no abstraction | Keeps adding a second brush later to a matter of a new implementation rather than restructuring stroke capture/rendering, without committing to any product surface (control, config field) before there's a real need for one. |
| Who creates and owns a stroke's lifecycle | The active brush creates each stroke that begins under it; the created stroke, not the brush's caller, captures its own points and renders itself | A caller constructs a single, brush-agnostic stroke value holding a point list and a brush reference, and calls the brush's render function directly, passing that point list in each time | Lets a brush pair itself with whatever internal stroke representation its own rendering actually needs (e.g. a future brush whose points each carry their own color) without a shared stroke type needing to know about it. |
| Where a stroke's color lives | As a property of the stroke, resolved once from the brush's `ColorSource` at that stroke's own creation | (1) Fixed at the brush instance's own construction instead — required a fresh brush per stroke to vary color between strokes; (2) a separate color accessor alongside the brush accessor, with color passed to the brush's render call each time | Resolving per-stroke rather than per-brush-construction is what lets one long-lived brush instance answer for many differently colored strokes (see "Brush lifetime" below), matching a `ColorSource` like `RandomColor` that's meant to vary between strokes. This does mean a brush whose color changes mid-stroke (e.g. a future rainbow-cycling brush) no longer fits the simple-stroke model, since a stroke's color is fixed at its own creation rather than re-resolved per point — an accepted trade-off. |
| Brush lifetime | A single long-lived `Brush` instance, held and returned unchanged by `StyleSettings.getActiveBrush()` across every stroke | A fresh `Brush` constructed per stroke (the original design), carrying an already-resolved color from its own construction | Avoids allocating a throwaway `Brush` per stroke purely to carry one resolved color; the brush becomes a genuine reusable strategy object, matching what "brush" already implies, rather than a disposable per-stroke value wrapper. |
| `restart()` must not re-resolve color | `SimpleStroke.restart()` constructs its continuation directly, reusing the interrupted stroke's own already-resolved color, never calling back through the brush's `startStroke()` | Call `brush.startStroke(lastPoint)` from `restart()`, as when color was fixed at brush construction (safe then, since every call returned the same fixed color) | Now that a brush resolves a fresh color from its `ColorSource` on every `startStroke()` call, routing `restart()` back through it would silently resample a new color mid-touch, breaking the existing guarantee that an interrupted stroke's replacement carries the same color forward (see CANVAS-STYLE-011). |
| `StyleSettings` accessor naming and background's return type | `getResolvedBrush()`/`getResolvedBackground()` renamed to `getActiveBrush()`/`getActiveBackground()`; `getActiveBackground()` returns a `ColorSource` (a caller resolves and caches a `Color` from it itself) rather than a resolved `Color` directly | Keep `getResolvedBackground(): Color`, unchanged | Readability: both accessors now read as "the thing currently active," and background's shift to a caller-resolved `ColorSource` mirrors the brush's own shift to holding a `ColorSource` rather than a bare value — even though the caller's job (resolve once, cache until the next `clear()`) doesn't change either way. |
| `Point`'s package | Owned by Painting Style | Owned by Painting, as originally designed, with Painting Style taking a one-directional dependency on it | The coordinate system exists specifically to serve correct resize-adaptive rendering inside a brush's own `render()` call — a Painting Style concern — and moving it here makes every cross-domain dependency point the same direction (Painting/User Experience → Painting Style), removing the one case where it ran the other way. |
| `Point`'s coordinate basis | Both axes scaled by one shared factor — the shorter of the canvas's width and height — with the origin at the canvas's center | (1) Each axis scaled independently by its own dimension, as originally designed (distorts shape on an aspect-ratio-changing resize); (2) letterbox/pillarbox to a fixed aspect ratio (no distortion or overflow, but wastes screen space); (3) crop content that doesn't fit the new bounds | Uniform scaling preserves a stroke's shape exactly across any resize, including a device rotation, without needing to detect or special-case it. Centering makes any unavoidable overflow — which a rotation can trigger just like any other aspect-ratio-changing resize, since portrait's long axis becomes landscape's short one — symmetric rather than always spilling off one edge. Letterboxing and cropping were rejected — see Point. |
| Who owns stroke serialization | `Stroke.save()`/`Brush.restore()` — each brush's own concern, producing and consuming a self-describing `Map<String, Any?>` | External code (Painting's own persistence logic) reads a stroke's points and color directly, via a narrower marker interface or type cast | Keeps Painting's persistence code from needing to know how any particular brush's stroke is represented internally, the same encapsulation `startStroke()` already provides for live strokes. Restoration always asks the currently active brush to `restore()` a saved stroke rather than tracking which brush originally produced it (see Open Questions #4/#6) — exact by construction today, since only one brush type exists. |
| `SavedStroke` as a dedicated type vs. a plain `Map` | A plain `Map<String, Any?>`, no dedicated wrapper type | A named `SavedStroke` data class (or sealed hierarchy) with typed fields | The ultimate destination — Compose's saveable-state storage — is itself dynamically typed with no compile-time schema, so a named wrapper wouldn't add real type safety, only indirection. A `Map` is already the natural fit for Compose's own `mapSaver` helper, and different brush types can use entirely different map shapes without any shared type needing to accommodate them — the same flexibility a sealed hierarchy would provide, without needing one until a second brush type actually requires a different shape. |
| `AbstractSimpleBrush`'s stroke's internal point storage | Compose-observable (`mutableStateListOf<Point>`), satisfying Painting's requirement that a stroke's captured points participate in Compose's draw-phase snapshot observation (see the Painting LLD's Composable Shape) | (1) An immutable stroke — `addPoint()` returns a new copy-on-write instance, with the caller holding the current stroke via whole-value `mutableStateOf` replacement; (2) a plain `kotlinx.coroutines.flow.StateFlow<Int>` revision counter on the caller's side, incremented on every mutating call and collected once via `collectAsState()`, leaving `Stroke`/`Brush` free of any Compose import; (3) `Stroke` exposing its own change-signal (a `Flow` or custom emitter), collected by a bridging composable | Keeps `Stroke`'s existing mutating shape rather than restructuring around immutability or threading a revision/signal layer through its caller. All three alternatives stay viable if a real need to decouple Compose entirely from `Brush`/`Stroke` arises later (none has today) — recorded here so that need doesn't have to rediscover them from scratch. |
| `ColorSource` as a pluggable interface | `ColorSource` with a single `getNextColor(): Color` method, queried whenever a caller needs one | A plain `Color` value with no abstraction; a `Flow<Color>`-based reactive source | Mirrors `Brush`'s existing pluggable-strategy shape. A pull-based `getNextColor()` matches the query-driven cadence its callers already use (once per stroke, or at construction/clear for a background) — nothing needs to observe a color change between queries, so a reactive stream would be unused machinery. |
| HSV composed of three independent per-channel `Distribution`s | `RandomColor(hue, saturation, value)`, each an independent `Distribution` | A single joint distribution over RGB or HSV space; hardcoded, non-pluggable HSV sampling logic | Independent per-channel "dials" let each channel vary its own distribution shape (e.g. uniform hue, constant saturation, a linearly-weighted brightness) without a combinatorial explosion of joint-distribution classes for every combination. |
| `Distribution`'s randomness source | Each concrete `Distribution` holds its own `kotlin.random.Random`, injected at construction (default `Random.Default`) | `sample()` takes a `Random` parameter at call time; no injection at all, always `Random.Default` | Construction-time injection keeps each `Distribution` self-contained and lets a test substitute a scripted fake `Random` per instance without threading one through every caller and every intermediate composing type. |
| `LinearDistribution`'s sampling algorithm | A mixture of two monotonic branches (`sqrt(random.nextFloat())` and `1 - sqrt(random.nextFloat())`), chosen with probability proportional to the endpoint weights | Invert the distribution's CDF directly by solving the quadratic `(w1-w0)x² + 2w0x - U(w0+w1) = 0` for `x` | The mixture decomposition needs only elementary arithmetic and one square root, with no quadratic-root algebra or branch-sign pitfalls, and produces an identical distribution by construction (a weighted mixture of two linear densities is itself linear, landing exactly on the requested endpoint weights). |
| `LinearDistribution`'s weight parameters | Read only as a ratio (`weightAtMax / (weightAtMin + weightAtMax)`); default `(0, 1)` | Normalize weights internally to a fixed total; require weights to be probabilities summing to 1 | Since only the ratio matters, any two values in the same proportion are equivalent — so the default doesn't need to match the underlying density function's literal peak value (`2`, for a pure ramp from a zero endpoint); a bare `1` is the least surprising default for a "weight" on its own. |
| `StyleSettings` defined here but implemented outside | Painting Style owns the interface (and its `Brush`/`ColorSource` return types) but not an implementation | Also provide a default/no-op `StyleSettings` implementation here; leave the interface owned by Painting instead, as before this LLD existed | Unlike `ColorSource`/`Distribution`, which Painting Style both defines and implements, deciding what's "current" (a swatch tap, a config value) is inherently about screen orchestration — Painting Style owns only the vocabulary, not the decision. |
| `PowerDistribution` as a distinct type rather than extending `LinearDistribution` | A separate implementation sampling `random.nextFloat().pow(1f / exponent)` | Add an `exponent` parameter to `LinearDistribution` itself; only expose steeper bias via `LinearDistribution`'s existing weight parameters | `LinearDistribution`'s mixture algorithm can only ever produce a straight-line density; a curved (super/sub-linear) density needs a genuinely different sampling formula, not an extra parameter bolted onto the same one. The two stay complementary: `LinearDistribution` covers any straight-line density including a bias at both ends at once, `PowerDistribution` covers any single-ended curve steeper or shallower than a straight line. |

## Open Questions & Future Decisions

### Resolved

1. ✅ A brush is a single long-lived instance holding a `ColorSource`; color is resolved once per stroke, at that stroke's own creation, and held by the `Stroke` rather than the brush. See Brushes and Decisions & Alternatives.
2. ✅ `Point` moved from Painting's package into Painting Style, removing the one dependency that previously ran the other way. See Point and Decisions & Alternatives.
3. ✅ `StyleSettings.getResolvedBackground(): Color` became `getActiveBackground(): ColorSource`, alongside `getResolvedBrush()` becoming `getActiveBrush()`. See Style Settings and Decisions & Alternatives.
4. ✅ `Point`'s coordinate basis changed to uniform, center-anchored scaling by the canvas's shorter dimension, so a stroke's shape survives any resize including an aspect-ratio-changing one. See Point and Decisions & Alternatives.
5. ✅ `Stroke`/`Brush` gained `save()`/`restore()`, so a stroke can survive Painting's lifecycle-survival mechanism without external code needing to know how it's represented internally. See Save and Restore and Decisions & Alternatives.

### Deferred

1. The default brush's line width is a visual-design decision, not fixed here.
2. Whether the default brush needs path smoothing is deferred until its unsmoothed polyline is actually seen in practice.
3. Whether and how brush choice ever becomes user-facing — a Widgets control, an age-gated bundle entry, or otherwise — is not decided; today it's purely an internal architectural seam with a single implementation behind it.
4. How `getActiveBrush()` produces a correctly typed instance once more than one brush type exists — some kind of type-keyed factory, since each type may need its own construction arguments beyond a `ColorSource` — is deferred; today, with exactly one brush type, an implementation can just construct that one type directly.
5. `Distribution` and `ColorSource` have no consumer today beyond `RandomColor`'s three HSV channels and a brush's own color — whether either gets reused for something else (a randomized brush line width, for instance) isn't decided; the interfaces don't assume color as their only use.
6. How Painting's restoration mechanism identifies which brush *type* originally produced a saved stroke — so it can `restore()` on the right brush instead of always the currently active one — isn't decided; it depends on open question #4 above (how `getActiveBrush()` identifies brush type at all). Today, restoration always uses the active brush, which is exact by construction since only one brush type exists.
